작성일: 2026-09-09. 외부 평가 서비스 없이 로컬 파일로 관리한다. 현재는 사람이 검토할 초안이며 평가 실행 결과나 검증된 정답 세트가 아니다.

| retrieval.jsonl | 12 | 검색기 및 엔티티 조회 | 질문 검토; Silver 정답 ID 라벨링 대기 |

## 상태와 데이터 분할

- `review_required`: 기대 행동을 작성했지만 사용자 검토 전. 승인 후 `ready`로 변경한다.
- `awaiting_data`: 실제 정답 ID, 출처, 스냅샷 또는 기준 SQL이 필요하다. 평가 점수 계산에서 제외한다.
- `development`: 질문·프롬프트·검색 개선에 사용하는 공개 개발 평가 사례다. 학습 데이터로 자동 전환하지 않는다.
- `regression`: 기존 젠데이야 실패와 그 변형. 개발 과정에서 이미 알려진 사례이므로 미지의 질문에 대한 일반화 점수로 보고하지 않는다.
- 현재 `holdout`은 없다. 실제 데이터 확보 후 별도로 확보·검토하고, 모든 관련 질문 변형을 family 단위로 묶어 학습/개발/최종 평가 간 중복을 방지한다. 같은 영화·인물의 등장만으로 무조건 누출은 아니지만, 미지 인물 일반화 실험에서는 엔티티 단위 분리도 적용한다.

## 질문별 채점 원칙

### LLM 질문 해석

`expected`는 평가용 의미 계약이며 현재 애플리케이션 QueryPlan의 실제 필드명을 보장하지 않는다. 앱 스키마 어댑터를 만들어 의도·조건별로 비교하고 JSON 문장 전체 일치를 강요하지 않는다. `rubric`은 필수 행동 기준이다. 인물명 해석은 LLM만의 책임으로 강제하지 않고 인물 조회 도구로 위임하는 것도 허용한다. reference_date와 history를 입력에 함께 제공한다.

### 검색

`entity_relation`, `structured_filter`, `title_resolution`은 구조화/별칭 조회를 포함한 검색 파이프라인 평가다. `semantic_plot`, `semantic_review`가 BGE-M3 의미 검색의 주요 대상이다. 배우 출연작 전체 조회를 벡터 Top-K만으로 해결하도록 강제하지 않는다.

null 정답은 미라벨 상태다. 빈 배열은 스냅샷을 실제로 확인한 결과 정답이 없다는 뜻으로만 사용한다. 실제 SQL·출처 크레딧을 사람이 대조해 기대 ID를 확정한다. 검색 대상 문서 버전과 chunk ID를 고정하고 movie ID와 document ID 지표를 섞지 않는다. 영화 평가에서는 여러 chunk를 영화별로 중복 제거한다.

의미 검색은 여러 검색 방식의 후보를 모아 사람이 관련성 0(무관)/1(부분 관련)/2(직접 관련)를 판정한다. 현재 모델이 반환한 후보만 정답으로 삼지 않는다. 미판정 문서를 모두 확실한 오답으로 취급하지 않고 라벨 범위를 기록한다. Recall@K와 nDCG@K는 데이터 충분성에 맞게 해석한다. 출연작 전체 요청은 전체 집합의 precision/recall도 별도로 계산한다.

### DW

질문에 따른 지표 정의를 먼저 검토하고, 고정 스냅샷에서 사람이 확인한 기준 SQL과 결과를 저장한다. 모델이 생성한 SQL로 정답을 만들지 않는다. 누적 관객 수를 일별로 더하지 않는다. 박스오피스 API에서 수집한 범위만 평가하고 미수집 영화·날짜를 0으로 바꾸지 않는다. 결과 비교는 영화 ID·숫자·순서·동률 규칙을 사용한다.

### 고정 근거 답변

`fixture: true` 자료는 모두 가상이다. 실제 영화 데이터, 임베딩 검색 코퍼스, DW에 적재하지 않는다. 질문과 context를 모델에 전달하되 required_facts/forbidden_behaviors는 채점기에만 제공한다. 문구 일치 대신 사실·숫자·근거 사용을 검토한다. 처음에는 사람이 통과/부분통과/실패와 사유를 기록한다. 평가 대상 Qwen의 자기 채점만으로 점수를 확정하지 않는다.

이 6건은 RAG의 답변 생성 단계만 평가한다. 실제 검색부터 답변까지 이어지는 RAG 전체 평가는 Silver·서빙 데이터가 준비된 후 별도 구성한다.

## 다음 작업

1. 질문과 기대 행동을 검토하고 모호한 기준을 확정한다.
2. 검토 완료된 LLM·가상 근거 질문으로 로컬 베이스라인을 측정한다.
3. Silver 고정 스냅샷에 검색 정답 ID·출처를 연결한다. 리뷰 미확보 항목은 대기 상태를 유지한다.
4. Gold 고정 스냅샷에서 기준 SQL·정답 수치를 검토한다.
5. 별도 holdout을 확보한 후 베이스/개선 실험을 비교한다. 테스트 결과를 보고 반복 수정하는 세트는 개발 세트로 간주한다.
6. 모델보다 데이터·별칭·필터·검색 전략에 문제가 있으면 해당 부분부터 개선한다. 파인튜닝은 평가에서 필요성이 확인될 때 진행한다.

평가 결과는 질문 파일과 분리해 experiment_id, case_id, 데이터 버전, 모델 digest, 프롬프트 버전, 검색/생성 설정, 출력, 검색 ID, 점수, 판정 사유, 지연시간을 기록한다. 여러 설정을 한꺼번에 변경하지 않는다. 현재 40건은 빠른 오류 발견용이며 통계적으로 충분한 일반 성능 벤치마크라고 주장하지 않는다.
