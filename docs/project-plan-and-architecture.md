# Pop Talk DW — 기획 및 아키텍처 검토안

작성일: 2026-09-08 · 최종 갱신: 2026-09-09 · 버전: 0.5 · 상태: 사용자 검토용

변경 사항: 기존 사용자 화면·관리자 화면·WAS·챗봇 API·배치의 역할을 반영했다. 생성은 Gemini API를 기준선으로 사용하고, 로컬 임베딩과 Qwen3 8B QLoRA 파인튜닝을 단계적으로 평가한다. 공개 벤치마크, 검색 평가, Pop Talk Golden QA를 결합하고 E 원본 보관소와 D 실행 캐시를 분리했다.

이 문서는 현재까지의 대화와 기존 파일 확인 결과를 정리한 설계안이다. **확정 요구사항, 제안 설계, 검증 전 가정을 구분**하며, 클라우드 연결이나 전체 데이터 처리가 이미 성공했다는 의미는 아니다.

## 1. 프로젝트 목적

기존 Pop Talk의 영화 데이터와 신규 평점·선택적 리뷰 데이터를 통합하여, 재실행 가능한 DW 파이프라인과 관리자 분석 대시보드를 구축한다. 검증된 데이터를 로컬 영화 챗봇에 공급하고 다양한 자연어 질문에 대한 검색·응답 정확도를 평가한다.

핵심 결과물은 DW 파이프라인이다. 챗봇은 영화 기본정보, 평점, 리뷰, 추천, 개봉 일정 등 기존 기능 구조를 출발점으로 한다. 배우명 표기 차이는 개선 사례 중 하나이며 챗봇 전체 목적을 배우 검색으로 제한하지 않는다.

### 설계상 제안하는 세부 정책

- 연도 조건은 **국내 개봉일 2020-01-01 이후**로 정의한다. 제작연도와 구분한다.
- 재개봉은 별도 표시하고, 최초 개봉 기준인지 재개봉 포함인지 데이터 조사 후 확정한다.
- 성인물·에로물·다큐멘터리 제외를 별도 정책으로 기록한다. 다큐멘터리는 영화의 한 종류이며 이번 서비스의 제외 유형으로 취급한다.
- 원천은 보존하고 서비스 대상 마트에서 정책을 적용한다. 기존에 제거된 원본은 복원됐다고 가정하지 않는다.

### 기존 애플리케이션 구성과 재사용 경계

사용자가 설명한 실제 역할을 기준으로 한다. 과거 README에 남은 배포 주소·목 데이터 설명은 현재 운영 상태나 구현 완성도를 입증하지 않으며 코드·API 계약과 대조해야 한다.

| 기존 경로 (pop_talk-product 기준) | 기존 책임 | 이번 프로젝트의 적용 |
|---|---|---|
| pop_talk/apps/admin | 실제 사용한 관리자 프런트엔드 | 기존 관리 화면 기반에 DW 분석·품질 대시보드 추가 |
| pop_talk_fe | 사용자 프런트엔드 | 영화 탐색·상세·기존 챗봇 연동 화면 재사용 |
| pop_talk_was | 사용자·관리자 공통 일반 백엔드, 챗봇 API 제외 | 기존 API 계약을 점검하고 영화·회원·리뷰 및 분석 조회 API에 필요한 범위 재사용 |
| pop_talk_chatbot | 챗봇 API와 LangGraph 로직 | 별도 API 경계를 유지하고 CLOVA 의존성을 Gemini 생성 API와 로컬 임베딩으로 교체 |
| pop_talk_batch | 영화 메타정보 수집용 배치 | API 수집 코드를 재사용하고 신규 DW 적재·Airflow 작업과 연결 |

pop_talk 안의 다른 apps를 실제 서비스 백엔드로 임의 채택하지 않는다. 로컬 챗봇은 별도 화면의 이름이 아니라 챗봇 API·모델의 실행 위치를 의미한다. 사용자·관리자 화면이 사용하는 일반 API는 WAS, 챗봇 요청은 챗봇 API로 구분한다. 각 화면의 실제 챗봇 호출 위치·인증 방식은 코드에서 확인한다.

기존 기능 전체를 새로 개발하는 계획이 아니다. 기존 화면·기능의 재사용 가능성을 먼저 조사하고, 반드시 연결할 흐름과 수정이 필요한 기능을 목록화한다. 배포 도메인·환경변수·인증·DB 스키마는 신규 로컬 환경에 맞춰 재설정한다.

## 2. 비즈니스 질문과 결과물

| 사용자 | 질문 | 제공 결과 |
|---|---|---|
| 운영자 | 수집된 영화의 흥행은 어떻게 변했는가? | 관측 범위가 표시된 일별 흥행 추이 |
| 콘텐츠 담당자 | 평가가 좋은 영화는 무엇인가? | 출처별 평점·평가 수·최소 표본 조건 |
| 데이터 담당자 | 데이터와 매핑을 신뢰할 수 있는가? | 결측·중복·미매칭·신선도·작업 상태 |
| 챗봇 사용자 | 조건과 분위기에 맞는 영화가 있는가? | 조건 필터와 의미 검색을 결합한 추천 |
| 챗봇 사용자 | 이 영화 정보·평점·리뷰·개봉일을 알려 달라 | 확보된 출처와 기준일에 근거한 응답 |

대시보드는 조회된 자료 범위의 분석 결과를 제공한다. 시장 전체 통계, 매출 예측, 추천으로 인한 실적 상승을 입증한다고 주장하지 않는다. 리뷰와 흥행 비교는 우선 탐색·상관 분석이다.

MovieLens 32M에는 32,000,204개 평점이 있으며 관측 기간은 2023-10-12까지다. 2024년 이후 개봉작의 최신 반응을 공급할 수 없다. links.csv의 외부 ID만으로 KOBIS·KMDb와 직접 연결된다고 가정하지 않는다. [공식 README](https://files.grouplens.org/datasets/movielens/ml-32m-README.html)

### 데이터 규모의 구분

1. 전체 평점: PySpark 정제·집계의 단계별 처리 실험에 사용한다.
2. 영화 매핑 교집합: 2020년 이후 서비스 영화와 검증된 연결만 분석 마트에 사용한다.
3. 미매칭: 삭제 대신 이유와 후보를 보관하고 커버리지 지표에 반영한다.

전체 입력 수, 매칭 영화 수, 연결된 평점 수, 연도별 분포를 각각 보고한다. 6천 영화와 3,200만 평점을 모두 연결할 수 있다고 표현하지 않는다. 전체 평점 반복 처리나 대량 임베딩을 필수로 묶지 않는다.

리뷰는 영화 연결 키·본문·출처·작성일·수정/삭제 상태를 우선 확인한다. 사용할 수 있는 리뷰가 부족하면 리뷰 기능은 데이터 없음 안내를 제공하고, 감성 분석은 확장으로 남긴다. 평점을 리뷰 본문처럼 취급하거나 합성 리뷰를 실제 관객 반응으로 사용하지 않는다.

### 애플리케이션 연결 구조

```text
pop_talk_fe 사용자 화면 ─────────┐
                               ├─ 일반 요청 → pop_talk_was
pop_talk/apps/admin 관리자 화면 ┘                 |
                                                  ├─ 서비스 데이터
                                                  └─ DW에서 게시한 분석 마트

각 화면의 챗봇 기능 → pop_talk_chatbot → LangGraph
                                         ├─ 구조화 데이터 조회
                                         └─ pgvector + 로컬 임베딩 + Gemini 생성 API

pop_talk_batch 수집 코드 → Airflow/DW 파이프라인
Snowflake 검증 결과 → 로컬 동기화 → PostgreSQL 분석·검색 영역
```

WAS와 챗봇 API는 별도 프로세스·책임으로 유지한다. 프런트엔드가 Snowflake나 DB에 직접 접근하는 구조로 설계하지 않는다. 요청별 프록시·경로는 기존 계약 확인 후 결정한다.

서비스 원본(회원·리뷰·관리자 편집 등)과 DW가 게시하는 분석·검색 데이터를 별도 스키마 또는 테이블로 분리한다. Reverse ETL이 서비스의 사용자 입력·관리자 수정값을 덮어쓰지 않도록 컬럼 소유권을 정의한다. 필요 시 서비스 리뷰 변경을 별도 증분 추출해 DW로 보내며, DW가 다시 게시한 결과가 원천으로 재수집되는 순환을 막는다.

이 흐름은 목표 구성이다. 특히 Databricks 입출력과 원격 작업 제어는 초기 연결 실험으로 검증한다.

| 계층 | 기술·책임 |
|---|---|
| 로컬 실행 | WSL2 + Docker Compose. 서비스 설정·버전 고정 |
| 오케스트레이션 | Airflow. 작업 제어를 담당하며 멱등성 자체는 적재 로직에서 구현 |
| 원천 | 원형 CSV·JSON, 체크섬·수집 이력. Parquet는 정규화·교환에 사용 |
| 레이크하우스 | Databricks + PySpark + Delta. 정제·매핑·대량 평점 처리 |
| DW | Snowflake + dbt. 차원·팩트·공통 지표·품질 테스트 |
| 전송 | 로컬 Python 중계 또는 검증된 커넥터. 초기 실험 후 하나를 선택 |
| 서빙 | PostgreSQL + pgvector. 승인된 분석 결과와 검색 데이터 |
| 모델 | 로컬 BGE-M3 임베딩 후보 + Gemini 생성 API 기준선 + Qwen3 8B QLoRA 비교 후보 |
| 화면·API | 기존 사용자 FE·admin·WAS·챗봇 API를 기반으로 필요한 흐름 연결. 관리자에 분석 화면 확장 |

### 무료 환경에 대한 결정 규칙

Databricks Free Edition은 서버리스·사용량 제한 환경이며 기본 외부 접근에 제한이 있다. 계정 조건에 따라 일부 기능이 확대될 수 있으므로 S3·Snowflake 연결과 Airflow 원격 호출을 실제로 시험한다. 사용자 지정 워크스페이스 저장소 제한이 모든 외부 S3 접근 불가를 의미한다고 단정하지 않는다. [공식 제한사항](https://docs.databricks.com/aws/en/getting-started/free-edition-limitations)

Snowflake는 현재 30일·$400 체험을 안내하며 기간 또는 잔액 중 먼저 소진되는 조건을 따른다. 실제 마감은 계정 화면을 기준으로 한다. [가입 안내](https://signup.snowflake.com/) · [체험 조건](https://docs.snowflake.com/en/user-guide/admin-trial-account)

- S3는 AWS 크레딧이 확인될 때만 필수 경로에 포함한다. 외부 저장소·전송·요청 비용도 예산에 포함한다.
- 직접 연동이 제한되면 로컬에서 파일 업로드·결과 다운로드를 자동화할 수 있는지 검증한다.
- 자동 전송도 불가하면 수동 단계를 명시하고, 완전 자동화 목표 달성 여부를 따로 보고한다. 무료 제한을 유료 전환으로 해결하지 않는다.
- 작은 표본 → 중간 규모 → 전체 규모 순서로 확대한다. 전체 실행은 잔여 크레딧·사용량을 확인한 후 수행한다.
- Snowflake는 작은 warehouse, 자동 중지, 사용량 모니터링을 적용한다. 모니터 하나가 모든 비용을 차단한다고 가정하지 않는다.
- 로컬 스냅샷은 종료 후 시연용이며 Snowflake/dbt 전체 실행을 로컬에서 동일하게 재현한다는 뜻은 아니다.

## 5. 데이터 계층과 키 매핑

### 계층별 데이터 계약

- 원천: source, collected_at, request_scope, file_checksum, run_id를 기록한다. 기존 가공 파일은 legacy_export로 분류한다.
- Bronze: 원천 payload와 출처 메타데이터를 보존한다.
- Silver: 타입·날짜·문자열 정리, 중복 제거, 공통 영화·인물 ID, 정책 판단과 미매칭 상태를 저장한다.
- Gold: 행 단위와 지표 정의가 고정된 차원·팩트·마트를 만든다.
- Serving: 검증을 통과한 배치 버전만 게시한다. source_as_of와 published_at을 구분한다.

### 영화·인물 매핑

제목·감독·연도는 후보 비교 근거이며 영구 식별자로 사용하지 않는다. canonical_movie_id와 person_id를 별도로 발급한다.

1. 정규화 제목·영문 제목·대체 제목으로 후보 생성.
2. 제작연도와 국내 개봉일을 구분하고 감독·국가·상영시간 등을 비교.
3. 확신이 높은 후보만 확정. 동점·충돌은 검수 대기.
4. source ID, 방법, 점수, 상태, 규칙 버전, 근거를 보관.
5. 매핑 수정 시 영향을 받은 팩트·마트·서빙을 재처리.

기존 매칭 함수는 제목·제작연도 중심이며 감독명은 검색어 확장에 사용한다. 이를 기준선으로 삼되 정확성은 검수 표본으로 평가한다. 인물 별칭도 출처를 기록하며 동명이인을 강제로 합치지 않는다.

## 7. 배치·품질·복구 설계

### 배치 경로

```text
입력 manifest 확정 → Bronze 적재 → Silver 정제·매핑
→ Silver 검증 → Snowflake staging → dbt build
→ 계층 간 대사 → serving staging → 배치 게시
→ 변경 문서 임베딩 → 검색 버전 게시 → 실행 결과 기록
```

초기 데이터 이관, API 일일 갱신, 선택적 외부 데이터 갱신, 서빙/임베딩 갱신을 구분한다. 초기에는 API 실측을 바탕으로 실행 시간을 정하고, 체험 동안 필요한 기간을 우선 수집한다. 무조건 2020년부터 전 날짜를 재수집하지 않는다.

- 업무 키와 입력 체크섬 기반 MERGE/UPSERT로 중복 방지.
- 실패한 실행은 마지막 정상 게시본을 유지하고 미완료 단계부터 재시도.
- 데이터 적재 성공 후 체크포인트 갱신. 이중 실행·부분 성공을 시험.
- 지연·정정 데이터는 겹치는 날짜 구간을 재수집하고 같은 관측 키를 갱신.
- 삭제·게시 중단은 tombstone 또는 상태값으로 문서·벡터에도 전달.
- 수정된 source ID 매핑의 영향 범위를 기록해 백필.

Airflow는 재시도와 실행 관리를 제공하지만 작업의 멱등성을 대신 만들지 않는다. [공식 모범 사례](https://airflow.apache.org/docs/apache-airflow/stable/best-practices.html)

### 품질 항목

| 종류 | 검증 |
|---|---|
| 키 | not_null, unique, 참조 무결성, 매핑 충돌 |
| 정책 | 개봉일 조건, 제외 유형의 서비스 마트 유입, 미상 값 처리 |
| 평점 | 출처별 범위·단위, 평가 수, 중복 관측 |

| 검색 | 문서 해시, 모델·벡터 차원·버전, 삭제 전파 |

dbt 기본 테스트와 위반 레코드를 반환하는 SQL 테스트를 병행한다. S3·Delta·pgvector는 별도 검사와 대사가 필요하다. [dbt data tests](https://docs.getdbt.com/docs/build/data-tests)

## 8. 로컬 챗봇 아키텍처

기준 문서: 기존 pop_talk_chatbot/docs/langgraph_flow.html. 아래는 해당 문서의 설명을 해석한 것이며 실제 코드와 동일한지는 구현 전 확인한다.

```text
입력 검증 → 의도 분류 → 구조화 QueryPlan
→ 영화·인물·대화 맥락 해석 → 기능별 데이터 조회
→ 답변 생성 → 근거·조건 검수 → 최종 응답
                         └ 실패 원인별 제한된 재시도
```

### 기존 기능의 신규 적용

| 기능 | 계획 |
|---|---|
| 기본정보 | 정규화된 영화 메타데이터 조회 |
| 평점 | 출처·평가 수·기준일을 포함한 마트 조회 |
| 리뷰 / 평점+리뷰 | 본문 확보 시 적용. 표본 요약과 전체 반응을 구분 |
| 추천 | 장르·인물·국가·연도·시간 등 필수 조건과 의미 검색 결합 |
| 취향 | 기존 FE·WAS의 회원·취향 계약을 우선 점검. 시연용 프로필 대체는 일정상 필요한 경우의 대안 |
| 개봉 일정 | 확보한 날짜 범위만 응답. 예정작 포함 가능 여부 별도 확인 |
| YouTube 링크 | 별도 API·무료 쿼터 확인 후 선택 기능 |
| 검수·폴백 | 근거·숫자·조건 확인, 데이터 없음과 미지원 출처 구분 |

QueryPlan에는 title, actors, directors, genres, countries, dates, runtime, rating_source, keywords, avoid_keywords, limit, sort 등의 검증된 필드를 둔다. 명시적인 필수 조건과 선호 조건을 구분한다. 검색 실패 시 필수 조건을 조용히 제거하지 않는다.

배우명 오타·표기 차이는 인물 ID 해석에서 처리한다. 분위기·줄거리 질문은 의미 검색을 사용하고, “그중 2시간 이하”는 이전 후보와 조건을 결합한다. 필모그래피 응답은 수집된 서비스 범위임을 표시한다.

기존 그래프의 리뷰 조회는 문서상 SQL 기반이다. 이번에 모든 기능을 벡터 검색으로 바꾸지 않는다. 내부 근거 ID와 별개로 화면에는 사용자가 이해할 수 있는 출처·기준일을 제공한다. 높은 별점 리뷰만 요약하는 편향과 인용 형식만 맞고 내용은 틀리는 문제를 별도로 검사한다.

### 모델·자원 운영

- 임베딩 후보: BGE-M3 등 한국어 평가 가능한 로컬 모델. 모델·배치 크기는 실측 후 확정.
- 기본 생성 경로는 로컬 규칙 의도 분류 → Gemini QueryPlan → 검색 → Gemini 답변 → 로컬 근거 검수로 운영.
- Gemini 의도 분류와 Gemini 답변 검수는 평가 시 선택적으로 켠다. 현재 계정에서 확인한 Gemini 2.5 Flash 무료 한도는 모델당 하루 20회였으므로 기본 경로를 질문당 약 2회 호출로 제한한다.
- Gemini 3 계열은 무료 사용 가능 모델과 계정별 할당량을 확인한 뒤 별도 기준선으로 시험한다. 프리뷰 별칭보다 사용 가능한 안정 모델 ID를 우선한다.
- 문서 임베딩 배치는 로컬 GPU에서 실행하고, 질문 임베딩도 같은 모델·전처리를 사용.
- Gemini에는 검색된 최소 근거만 전달하고 사용자 식별정보를 제거. 무료 티어의 데이터 이용 조건을 시연 데이터 범위에서 검토.
- 기존 CLOVA 벡터와 새 벡터는 같은 인덱스에 혼합하지 않음.
- 숫자 평점 전체는 임베딩하지 않음. 줄거리·선별된 리뷰만 대상.
- content_hash, model_version, chunk_version이 달라진 문서만 재처리.
- Airflow 메타데이터 DB와 서빙 DB는 논리적으로 분리. 워커는 스케줄러 밖에서 실행.

[BGE-M3 모델 카드](https://huggingface.co/BAAI/bge-m3) · [LangGraph 개요](https://docs.langchain.com/oss/python/langgraph/overview)

### 로컬 생성 모델과 파인튜닝 계획

로컬 모델은 Gemini 장애 시 즉시 대체하는 완성 모델로 가정하지 않는다. 먼저 동일 질문·동일 검색 근거로 기준 성능을 측정하고, 실패 사례에서 학습 데이터를 만든다. 12GB VRAM에서는 전체 파라미터 학습 대신 4bit QLoRA를 사용한다.

| 단계 | 모델·방식 | 목적 | 통과 기준 |
|---|---|---|---|
| 1. API 기준선 | Gemini Flash | QueryPlan과 근거 기반 답변의 목표 품질 확보 | 평가 질문별 정답·지연시간·호출 수 기록 |
| 2. 로컬 기준선 | Qwen3 8B 양자화 | 파인튜닝 전 한국어·JSON·근거 답변 성능 측정 | 동일 평가 세트로 Gemini와 비교 가능 |
| 3. 행동 학습 | Qwen3 8B 4bit QLoRA | 의도·조건 추출, QueryPlan, 근거 인용, 데이터 없음 응답 개선 | 홀드아웃 데이터에서 기준선보다 개선 |
| 4. 선택 비교 | Gemma 3 12B QAT 등 | 12GB VRAM에서 품질·속도 상한 확인 | 메모리 초과 없이 제한 문맥에서 측정 |
| 5. 단계적 적용 | 공급자 설정으로 Gemini/로컬 전환 | QueryPlan부터 로컬화하고 답변 생성을 후속 전환 | 폴백·API 계약·회귀 테스트 통과 |

Ollama에서 받는 양자화 GGUF는 우선 추론용이다. 학습은 Hugging Face 형식 원본 모델과 별도 LoRA adapter로 진행하고, 검증된 adapter만 병합·GGUF 변환하여 Ollama에 게시한다. `base_model`, `base_revision`, `adapter_version`, 학습 데이터 버전, 프롬프트 버전, 양자화 방식을 manifest에 기록한다.

파인튜닝은 영화 사실을 암기시키는 용도로 사용하지 않는다. 최신 평점·흥행·개봉 일정·리뷰 사실은 DW와 RAG가 제공한다. 학습 대상은 다음과 같다.

- 영화 정보·평점·리뷰·추천 의도 및 복합 조건 분류.
- 배우·감독·제목과 별칭, 이전 대화의 지시어를 QueryPlan 필드로 변환.
- 검색 근거 ID 인용, 스포일러 제외, 근거가 없을 때 추측하지 않는 행동.
- 한국어 답변 형식과 JSON 스키마 준수.

학습 데이터는 운영 로그 원문을 그대로 사용하지 않는다. 평가용 질문과 정답 QueryPlan을 사람이 검수하고, 사용자 식별정보를 제거한 뒤 train/validation/test로 분리한다. 동일 영화나 문장 변형이 학습·평가 세트에 동시에 들어가 점수가 부풀지 않도록 그룹 단위로 분할한다.

임베딩 파인튜닝은 생성 모델과 별개다. BGE-M3 기본 성능을 먼저 측정하고, 배우명 변형·한국어 의미 검색에서 부족함이 확인될 때만 `질문-정답 문서-어려운 오답` 데이터로 후속 학습한다. 숫자 평점과 시계열 지표는 계속 구조화 조회를 사용한다.

모델은 `D:\01.DEV\pop_talk_dw_project\.local\models\ollama`에서 먼저 관리·실행한다. 외장 E 드라이브에서는 Qwen3 8B 첫 로딩과 6.4GB 복사·해시 검증이 매우 느렸고 중단된 복사에서 손상 blob이 확인됐다. 따라서 모델·adapter·평가 결과는 D에서 안정화한 후 SHA-256 검증을 거쳐 `E:\PopTalkAI`에 백업한다. 평상시 Ollama 서버는 11434 포트 하나만 실행하고 여러 서버가 동시에 GPU 모델을 적재하지 않는다. 세부 절차는 [로컬 모델 저장·실행 정책](local-model-storage.md)을 따른다.

## 9. 사용자·관리자 활용 화면

사용자 화면은 pop_talk_fe를 기반으로 영화 탐색·상세 및 기존 챗봇 진입 흐름을 신규 API·DB에 연결한다. 배우명 검색 외에도 기본정보·조건 추천·대화 맥락 등 기존 챗봇 기능을 평가한다. 리뷰 작성·회원·취향 기능의 실제 동작과 이식 범위는 코드 조사 후 기록한다.

관리자 화면은 pop_talk/apps/admin을 기반으로 기존 관리 기능과 아래 분석 기능을 연결한다. 기존 관리자 기능을 대시보드로 대체한다는 의미가 아니다.

1. 영화·흥행: 기간별 관측 실적, 영화·장르 필터, 데이터 범위 표시.
2. 평점: 출처별 평균·평가 수·분포·최소 표본 조건. 결측과 0 구분.
3. 데이터 품질: 매핑률·충돌·미매칭·결측·최신 수집일·배치 실패.
4. 선택적 리뷰: 실제 확보된 영화에만 주제·반응 분석.

관리자 분석 화면은 WAS의 분석 조회 API를 통해 PostgreSQL에 동기화된 결과를 사용하여 매 화면 요청마다 Snowflake를 깨우지 않는다. 실시간 조회가 아니라 게시 시점 기준의 결과임을 표시한다. 일반 서비스 요청과 챗봇 요청의 인증·권한 경계를 각각 검증한다.

### 제안 평가 기준

평가는 한 종류의 점수로 결론 내리지 않고 다음 세 층으로 분리한다. 공개 벤치마크는 기본 모델 선택에 사용하고, 프로젝트의 최종 성공 여부는 실제 DW 정답과 연결된 Pop Talk 전용 평가 세트로 판단한다.

| 평가 층 | 목적 | 후보·지표 | 프로젝트에서의 판단 범위 |
|---|---|---|---|
| 범용 모델 | 한국어 이해·일반 추론·기본 임베딩 능력 비교 | KMMLU, KoBEST, MTEB 등 공개 결과 | 모델 후보를 좁히는 참고 자료이며 서비스 합격 기준으로 단독 사용하지 않음 |
| 검색·RAG | 올바른 영화·리뷰·근거 검색 확인 | Recall@K, MRR, nDCG, 근거 정밀도 | 벡터 검색, 구조화 조회, 두 방식을 결합한 검색을 동일 질문으로 비교 |
| 서비스 업무 | 실제 Pop Talk 질문을 끝까지 정확히 처리하는지 확인 | Golden QA의 QueryPlan·엔티티·팩트·근거·응답시간 | 챗봇과 파인튜닝의 주 합격 기준 |

RAGAS·DeepEval 같은 도구는 자동 평가 실행에 사용할 수 있지만 그 자체가 이 영화 서비스의 정답 데이터는 아니다. 자체 LLM 검수 점수만 성과로 사용하지 않고, SQL 결과·영화 ID·집계값처럼 재현 가능한 정답을 우선한다.

#### Pop Talk Golden QA 세트

초기 목표는 150~300문항이다. DW 구축과 챗봇 이식을 먼저 검증하는 최소 단계에서는 60~100문항으로 시작하고, 파인튜닝 비교 전까지 아래 범위를 확장한다.

| 질문 유형 | 목표 문항 수 | 주요 검증 항목 |
|---|---:|---|
| 제목·감독·배우 검색 | 40 | 엔티티 매핑, 한글·영문·별칭·표기 변형 |
| 복합 조건 검색 | 40 | 연도·장르·국가·인물·상영시간 조건의 동시 충족 |
| 평점·흥행 분석 | 40 | DW 집계값, 기간 조건, 누적값과 일별값 구분 |
| 리뷰 요약·반응 | 30 | 실제 리뷰 존재 여부, 검색 근거와 요약의 일치 |
| 추천 | 30 | 필수 조건 충족, 추천 근거와 중복 억제 |
| 데이터 없음·모호한 질문 | 20 | 추측 억제, 재질문 또는 데이터 없음 응답 |
| 오타·별명·외국어 표기 | 20 | 배우·감독·영화명의 변형에 대한 정규화 |

각 사례는 자연어 정답만 저장하지 않고 다음 계약을 따른다.

```json
{
  "question_id": "actor_alias_001",
  "question": "젠다야가 나온 2020년 이후 영화 알려줘",
  "intent": "movie_search",
  "expected_entities": {
    "actor": "젠데이아",
    "release_year_gte": 2020
  },
  "expected_movie_ids": ["MOVIE_001", "MOVIE_027"],
  "acceptable_answer_facts": ["영화 제목", "개봉연도", "출연 근거"],
  "must_not_include": ["출연하지 않은 영화"],
  "difficulty": "hard"
}
```

Golden QA 후보는 Snowflake 또는 PostgreSQL의 검증 SQL 결과에서 영화 ID와 집계값을 뽑고, 질문 템플릿과 표기 변형을 적용해 반자동으로 만든다. 사람이 질문의 자연스러움, 기대 조건, 정답 ID를 최종 검수한다. 평가 세트에는 사용한 DW 스냅샷 ID와 SQL 또는 정답 생성 규칙을 기록해 데이터가 바뀌어도 결과를 재현할 수 있게 한다.

#### 측정 지표와 비교 실험

- 데이터 파이프라인: 검수용 영화 매핑 약 200쌍의 정확도·커버리지·충돌률, 동일 입력 재실행 시 중복 증가 0건, 부분 실패·날짜 누락·매핑 수정·삭제의 복구 결과.
- 처리 성능: 행 수·시간·환경·크레딧 사용량을 함께 기록. 무료 서버리스를 통제된 클러스터 확장 실험으로 표현하지 않는다.
- QueryPlan: 의도 정확도, 필드별 조건 정확도, 전체 조건 Exact Match, 유효 JSON 생성률.
- 검색: Entity 정확도, Recall@K, MRR, nDCG, 필수 조건 위반률.
- 최종 답변: DW 숫자·팩트 정확도, 근거 충실도, 데이터 없음 정확도, 응답시간.
- 모델 운영: 동일 질문과 동일 검색 근거로 Gemini와 로컬 Qwen3의 JSON 성공률·근거 충실도·응답시간·VRAM·호출 비용을 비교.
- 검색 전략: 벡터 단독 기준선과 구조화 조회 결합안을 같은 데이터·질문으로 비교.

#### 파인튜닝 데이터 분리

Golden QA 원본을 먼저 고정한 뒤 학습 70%, 검증 15%, 최종 평가 15%로 분리한다. 동일 영화나 동일 템플릿의 단순 표현 변경이 학습 세트와 최종 평가 세트에 동시에 들어가 정답이 누출되지 않도록 그룹 단위로 분리한다. 최종 평가 세트는 QLoRA 학습과 프롬프트 수정 과정에서 열람·사용하지 않으며, 파인튜닝 전 로컬 모델과 파인튜닝 후 모델을 같은 세트로 비교한다.

평가 표본 수와 합격 임계값은 제안값이며 실제 기준선 측정 후 확정한다.
