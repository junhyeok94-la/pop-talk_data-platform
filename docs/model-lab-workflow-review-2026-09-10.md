# Model Lab 공용 MLOps 흐름 검토안

검토일: 2026-09-10. 현재 플러그인·실행기·챗봇 코드와 프로젝트 평가 계약을 읽고 작성한 **설계 제안**이다. 아래 목표 화면·API·DAG가 구현되었다는 의미는 아니다.

## 판단

Model Lab의 중심을 **버전이 고정된 실험과 그다음 행동**으로 바꾸는 것을 권한다.
사용자가 기준선을 만들고 실패 원인을 확인한 뒤, 프롬프트·검색 설정·모델·학습 중 필요한 것을 바꾸고 같은 조건으로 다시 평가할 수 있어야 한다.
학습은 이 과정의 선택 가능한 단계다. 프로젝트 데이터와 채점 규칙은 프로젝트 프로필로, 실제 계산은 등록된 실행 대상으로 연결한다.

현재 외부 학습 실행의 기반은 있으나, 평가 → 학습 → 산출물 → 재평가 → 서비스 적용의 연결이 부족하다.
탭을 더 늘리는 것보다 공통 실행 기록, 데이터·모델 버전, 평가 결과의 연결을 먼저 구현해야 한다.

## 현재 구현에서 확인한 공백

[실험 잠금](../orchestration/airflow/plugins/airflow_workbench/store.py)은 `ollama` 하나다. | 학습 환경을 바꿔도 평가 대상은 별도로 선택할 수 없다. 독립 GPU 두 대도 평가를 병렬 실행하기 어렵다. | 추론 연결·학습 실행 대상·공유 자원 그룹을 구분해 등록하고 실험에 선택값을 고정한다. |

| 우선 | 생성·임베딩 결과는 `experiments`, 학습은 DAG 실행과 외부 job에 나뉜다. | 어떤 기준선을 개선하려고 학습했는지, 그 산출물이 어떤 재평가를 거쳤는지 연결되지 않는다. | 하나의 실험에 기준선·후보 실행·학습·패키징·평가를 연결한다. 실행 유형은 보존한다. |

| 우선 | 실험·프리셋·환경은 공용이고 [권한](../orchestration/airflow/plugins/airflow_workbench/app.py)은 Plugins 조회와 관리/custom 변경 권한 중심이다. | 한 설치에서 여러 프로젝트를 운영하면 입력 원문·실험·환경이 섞인다. 일반 실험 담당자와 환경 관리자의 역할도 나누기 어렵다. | 프로젝트 단위 접근 검사와 작업별 권한을 적용한다. 단일 프로젝트 설치는 기본 프로필을 자동 선택한다. |
| 다음 | [학습 결과](../orchestration/model_worker/train.py)는 모델/adapter·metrics·receipt 파일이다. 모델 등록·추론 패키징·승격은 없다. | 학습 성공 후 모델 목록에서 후보를 선택해 다시 비교할 수 없다. | 산출물을 모델 버전으로 등록하고 평가용 런타임 준비를 연결한다. |
| 다음 | [환경 계약](../orchestration/airflow/plugins/airflow_workbench/environments.py)은 HTTP/Kubernetes를 지원하지만 [제공 워커](../orchestration/model_worker/worker.py)의 workload/profile은 고정 목록이다. 참조 학습기는 CUDA·FP16·단일 GPU 중심이며 checkpoint 재개는 없다. | 다른 학습기·CPU·분산 학습을 환경 설정만으로 사용할 수 있다고 오해할 수 있다. | 실행기 지원 기능과 파라미터 스키마를 조회한다. 참조 워커의 지원 범위와 확장 실행기의 범위를 명확히 표시한다. |
| 다음 | 학습 폼은 SFT/임베딩에 같은 방법·LoRA 옵션을 보여준다. 유효하지 않은 조합은 서버에서 거부한다. | 임베딩을 선택하고 QLoRA를 그대로 둔 경우처럼 검증 버튼을 눌러야 오류를 알게 된다. | workload를 고르면 지원 방법만 제공하고 관련 없는 필드는 숨긴다. 모델·실행기별 지원 조합으로 폼을 구성한다. |
| 다음 | [Kubernetes 사전 검사](../orchestration/airflow/plugins/airflow_workbench/portable_training.py)는 namespace의 Pod 목록 조회, [취소 API](../orchestration/airflow/plugins/airflow_workbench/app.py)는 HTTP 작업을 지원한다. | 연결 성공을 GPU 확보로 오해하거나, 실행 방식마다 취소·로그 확인 위치가 달라진다. | 연결/입력 검증과 실제 admission을 별도 상태로 표시하고 공통 실행 상세에 backend별 제어를 연결한다. |
| 다음 | HTTP 완료 참조는 worker의 artifact ID, Kubernetes는 객체 저장소 URI다. metrics.jsonl이 있지만 공통 조회 API는 없다. | 학습 곡선·결과·로그가 한 화면에서 이어지지 않는다. | 실행기별 결과를 공통 manifest로 정규화하고 요약·다운로드·외부 로그 링크를 제공한다. |

유지할 기반은 PostgreSQL 단일 메타 저장, Airflow 인증, 환경 설정 fingerprint, DAG 계약 검사, 외부 실행, deferral, Pool의 deferred 점유, 작업 중복 제출 방지다.
이번 검토에서 모델 학습이나 서비스 적용을 추가 실행하지 않았다. 기존 검증은 [현재 화면 안내의 검증 범위](../orchestration/airflow/plugins/USER_GUIDE.md)에 명시되어 있다.

## 권장 사용자 흐름

```text
프로젝트 선택 · 기본 프로필
  → 연결과 실행 대상 확인
  → 데이터·평가셋 버전 확정
  → 기준선 평가
  → 실패 사례 분석
  → 개선 선택: 프롬프트 / 검색·인덱스 / 모델 교체 / 파인튜닝
  → 후보를 동일 평가셋으로 평가
  → 비교·검토
  → 검증된 모델 또는 검색 구성 등록
  → 테스트 서비스 적용 → 운영 적용 → 관측·되돌리기
```

이미 준비된 데이터·모델·환경은 재사용한다. 평가만 할 때는 학습 환경과 학습 DAG 준비를 요구하지 않는다. 학습이나 서비스 적용 없이 평가 결과를 등록하고 종료하는 것도 완결된 경로다.

| 단계 | 사용자가 하는 일 | 시스템이 이어서 처리할 일 | 남겨야 하는 결과 |
|---|---|---|---|
| 최초 준비 | 프로젝트 프로필, 추론 연결, 필요한 실행 대상 선택 | 지원 기능·Connection·권한 확인, 필요한 DAG 배포 상태 확인 | 버전이 있는 프로젝트/연결/실행기 설정 |
| 데이터 준비 | 기존 데이터·평가셋 선택 또는 파일/URI 등록 | 스키마·분할·라벨 상태 확인, manifest 생성, 필요하면 기존 데이터 준비 DAG 실행 | 데이터/코퍼스/평가셋 버전과 검사 결과 |
| 기준선 | 모델 또는 서비스 구성과 평가셋 선택 | 원본·추론 버전, 프롬프트·파라미터를 고정해 실행 | 기준선 실행, 사례별 결과, 요약 지표 |
| 분석 | 실패 유형·사례 확인 | 후보와 비교 가능한 조건 안내, 관련 개선 경로 연결 | 개선 가설과 기준선 참조 |
| 개선 | 설정 변경, 모델 교체, 인덱스 생성 또는 학습 레시피 작성 | 지원 옵션만 제공, 예상 자원과 제한 확인, 작업 제출 | 후보 설정/학습 실행/산출물 |
| 재평가 | 같은 평가셋으로 후보 평가 | 필요시 추론용 패키징·임시 엔드포인트 준비, 평가 실행 | 기준선 대비 변화, 회귀 사례, 자원·지연시간 |
| 등록 | 사용할 후보와 검토 사유 확정 | 모델 버전·평가 근거·관련 인덱스 연결 | 사용할 수 있는 후보 버전 |
| 적용 | 대상 서비스와 적용 버전 선택 | 프로젝트 배포 방식으로 적용, 상태 확인, 이전 버전 보관 | 서비스가 실제 사용하는 버전과 적용 이력 |
| 관측 | 지연·오류·품질 표본 확인 | 문제를 해당 모델·데이터·실행까지 추적 | 회귀 평가 또는 되돌리기로 연결 |

각 단계는 항상 현재 상태, 진행을 막는 이유, 실행 위치, 다음 행동을 보여준다. 예를 들어 “학습 데이터 미등록 → 데이터 등록”, “DAG 반영 대기 → 현재 파싱 상태 보기”로 연결한다. 탭을 옮겼다가 돌아와도 초안과 선택한 프로젝트·모델·평가셋은 유지한다.

## Model Lab 안의 화면 구성

Airflow 왼쪽 **Model Lab** 안에서 아래 탭을 사용한다. 기존 Airflow 화면의 표·필터·상태 배지·상세 링크를 유지한다.

| 탭 | 역할 | 주요 행동 |
|---|---|---|
| 개요 | 준비 상태, 진행 중 실행, 최근 비교, 적용 중 버전 | 빠른 테스트 / 새 실험 / 중단된 단계 이어가기 |
| 데이터·평가셋 | 데이터와 평가셋 버전, 라벨·분할·검사 상태 | 등록 / 검사 / 새 버전 / 사례 검토 |
| 실험 | 기준선과 후보를 연결하는 실험 작업 공간 | 생성·임베딩·에이전트 평가 / 개선 후보 / 학습 레시피 |
| 실행 | 평가·학습·변환·인덱스 생성 등의 통합 실행 이력 | 상태·로그·지표·산출물 / 취소 / 새 시도 |
| 모델·릴리스 | 원본·튜닝 모델, 추론 패키지, 적용 버전 | 평가 / 후보 등록 / 서비스 적용 / 되돌리기 |
| 환경·연결 | 추론 endpoint, 학습 실행기, 저장소, 배포 대상 | 연결 검사 / 기능 확인 / DAG 설정 배포 |

현재 생성 모델 비교와 임베딩 평가는 **실험 → 빠른 테스트**로 이어받는다. 파인튜닝 설정도 실험의 후보 생성 방식으로 들어간다. `실행·리소스`에 섞여 있는 환경 설정과 실행 이력은 각자의 탭으로 분리한다.

실험 상세에는 기준선, 후보, 평가셋 버전, 변경한 설정, 사례별 결과, 관련 학습과 서비스 적용을 한곳에 표시한다. 편집 가능한 초안과 제출 시 고정한 실행 입력을 구분한다.

## 프로젝트 공용 구조

### 서로 다른 세 가지 연결

1. **추론 연결**: Ollama, 지원하는 OpenAI 호환 API, 또는 프로젝트의 평가 대상 API. 모델 목록·생성·임베딩·구조화 출력 등 실제 지원 기능을 표시한다.
2. **실행 대상**: HTTP Job API, Kubernetes 등 평가·학습·변환을 수행할 계산 환경. GPU가 필요한 작업만 GPU를 요청한다.
3. **적용 대상**: 챗봇·검색 서비스·배치 추론 등 실제 소비자. 배포 API 또는 기존 Git/CI 배포 과정과 연결한다.

같은 장비에서 세 역할을 맡을 수도 있지만 각각의 책임과 선택값은 구분한다. 어느 추론 서버가 어느 학습 실행기와 GPU를 공유하는지는 별도의 자원 그룹으로 표현한다.

공통 플러그인은 프로젝트·실험·실행·버전·지표·산출물·권한을 관리한다. 프로젝트 프로필에는 데이터 스키마, 평가 대상, 채점 규칙, 기본 프롬프트, 허용 실행기, 적용 대상이 들어간다. 영화·인물·평점 필드와 Qwen/BGE 이름은 현재 프로젝트 프로필의 값이다.

workload 템플릿은 지원하는 데이터 스키마, 파라미터와 범위, 필요한 기능, 결과 지표·산출물을 정의한다. 실행 코드는 관리자와 기존 배포 과정에서 관리하는 이미지/패키지로 공급한다. 사용자 폼에 임의 Python이나 shell을 입력하는 방식으로 범용성을 구현하지 않는다.

Ollama의 temperature/top-k와 다른 제공자의 파라미터가 전부 같은 의미이거나 지원되는 것은 아니다. 지원하지 않는 옵션은 실행 전에 표시하고, 적용된 최종 설정을 결과에 남긴다. 원격 API 모델의 내부 가중치 버전을 고정할 수 없는 경우에도 재현 가능 범위를 표시한다.

### 공통 저장 단위

| 단위 | 필수 연결과 책임 |
|---|---|
| Project | 구성·접근 범위·기본 프로필. 한 설치가 한 프로젝트면 기본값 사용 |
| DatasetVersion / EvaluationSuiteVersion | URI·checksum·split·스키마·라벨 상태·코퍼스/채점기 버전 |
| Experiment | 개선 목적·기준선·비교 후보·담당자 |
| Run / Attempt | 실행 종류·고정된 입력·상태·DAG run/task·외부 job·요청 중복 방지 ID |
| ModelVersion / Artifact | 원본 revision·adapter·학습 실행·tokenizer·형식·checksum·평가 결과 |
| Release | 적용 대상·모델/프롬프트/검색 버전 묶음·현재 실제 적용 버전·이전 버전 |

이 메타데이터는 기존 Airflow PostgreSQL의 `workbench` 스키마에 둔다. 데이터·가중치·상세 사례 결과·학습 로그는 파일/객체 저장소에 두고 DB에는 URI와 요약을 저장한다. 워커는 기존 endpoint/상태 API 방식으로 통신하며 DB 로그인은 추가하지 않는다.

MLflow처럼 모델 버전과 별칭을 분리하는 기존 방식을 참고할 수 있다. 다만 공통 레코드에 외부 registry ID를 연결할 수 있게 하고, MLflow 서버 설치를 플러그인 사용 조건으로 두지 않는 설계를 권한다. 별칭 변경과 서비스의 실제 적용 완료도 별도 기록한다. [MLflow 모델 버전·별칭](https://mlflow.org/docs/latest/ml/model-registry/workflow/#deploy-and-organize-models-with-aliases-and-tags)

실험은 기본적으로 프로젝트 내 협업 자산으로 두고, 개인 대시보드 설정과 분리한다. 프로젝트별 읽기·실험 실행·환경 관리·서비스 적용 권한을 검사한다. Airflow DAG tags는 분류 수단이며 접근 제어를 대신하지 않는다. 기존 공용 기록은 삭제하거나 소유자를 추정하지 않고 명시적인 기본 프로젝트로 이전하는 방안을 검토한다.

## 평가와 학습의 세부 흐름

### 생성 모델과 에이전트

빠른 질문 하나의 비교와 평가셋 전체 실행을 모두 지원한다. 기준선과 후보에는 평가셋·프롬프트·제공자·모델 버전·실효 옵션·실행 환경을 고정한다. 출력이 생성되었다는 사실과 출력 품질 통과를 구분한다.

에이전트는 모델 단독 생성과 별도의 평가 대상이다. QueryPlan/도구 호출/검색 결과/최종 답변을 단계별로 기록하고, 프로젝트의 평가 어댑터로 의미를 채점한다. 운영 세션·기억·도구 쓰기에 영향을 주지 않는 평가 endpoint 또는 격리된 실행 설정을 사용한다.

JSON 유효성·필수 필드·구조화 조건은 자동 검증하고, 근거 사용·답변 적합성은 프로젝트 규칙과 사람의 검토를 결합한다. 선택적으로 다른 평가 모델을 사용하더라도 평가 모델·프롬프트 버전을 기록하고 대상 모델의 자기 채점만으로 승격하지 않는다.

모델의 로딩 시간과 생성 속도, 처음 실행과 예열 후 실행을 구분한다. 제공자별 사용량이 없으면 0으로 보고하지 않는다. 결과 화면에는 전체 사례 수, 채점 가능 수, 미라벨·실행 실패 수, 지표 방향과 기준선 대비 변화가 있어야 한다.

### 임베딩과 검색

현재의 질문/문서 붙여넣기는 작은 동작 확인용으로 유지한다. 정식 평가는 질문 집합, 버전이 있는 코퍼스, 관련 문서 라벨과 검색 구성을 사용한다. 임베딩 단독 평가, 구조화 필터·별칭·재순위화를 포함한 검색기 평가, 답변 생성까지 포함한 RAG 평가를 선택할 수 있어야 한다.

정답의 없음·미라벨·부분 관련성을 구분하고, 문서/chunk/업무 엔티티 중 평가 단위를 명시한다. 프로젝트가 요구하는 graded relevance를 지원하며 여러 chunk가 같은 엔티티를 가리킬 때의 집계 규칙도 고정한다. 평가 라이브러리의 기존 검색 평가기를 재사용하고 입출력 계약을 감싼다. [Sentence Transformers 평가기](https://sbert.net/docs/package_reference/sentence_transformer/evaluation.html)

임베딩 후보의 적용 단위는 다음 묶음이다.

`모델 버전 + query/document 전처리 + 차원·정규화·거리함수 + 코퍼스 snapshot + chunk 설정 + 인덱스 버전`

새 임베딩 모델을 적용할 때는 해당 버전용 인덱스를 만들고 검색 품질·건수·실패 문서를 확인한 뒤 query embedding과 인덱스 참조를 함께 전환한다. 차원이 같더라도 서로 다른 벡터 공간을 섞지 않는다. 같은 모델의 데이터 변경분만 갱신하는 작업과 모델 변경으로 전체 대상 문서를 다시 임베딩하는 작업도 구분한다.

### 파인튜닝

레시피는 기준선과 개선 목적에서 시작한다. 원본 모델 revision, 학습기/이미지 버전, train/validation 데이터, 검증 방식, 자원 한도, 출력 위치를 고정한다. 최종 holdout은 파라미터 선택용 validation과 분리한다.

사전 검사는 입력 유효성 → 모델/학습기 호환성 → 데이터 검사 → 실행 환경 연결/배포 상태 → 제출 시 자원 확보 순서로 나눈다. Kubernetes 연결 성공이 Pod 생성·이미지 pull·가용 GPU 확보를 보장하지 않음을 화면 상태에 반영한다. CPU·GPU·RAM·디스크뿐 아니라 정밀도, 모델 크기, sequence length, batch, gradient accumulation, checkpoint 공간도 실행기가 검증해야 한다.

`ready`는 현재 검사 결과이며 예약을 뜻하지 않는다. 제출 시 버전과 자원을 다시 확인하고, 상황이 바뀌면 입력 초안을 유지한 채 원인을 보여준다. 실행기 보고에 없는 학습 가능 규모나 소요시간을 임의로 추정해 확정값처럼 표시하지 않는다.

단일 GPU 기준 실효 batch는 현재 식을 사용할 수 있으나, 분산 학습을 지원할 때는 world size까지 반영해야 한다. 여러 GPU를 Pod에 할당했다고 참조 학습기가 분산 학습기로 바뀌는 것은 아니다. checkpoint 저장·재개도 실제 학습기가 지원할 때만 노출한다.

### 산출물에서 실제 추론 모델까지

학습 완료 후 manifest를 검사하고 원본·adapter·tokenizer·chat template·학습 데이터·코드 버전을 모델 버전에 연결한다. 이후 목표 추론 엔진에 맞는 패키징/변환을 실행하고, 등록 → 로딩 검사 → 후보 평가로 연결한다.

HF adapter가 생성되었다고 곧바로 현재 Ollama에서 평가할 수 있다고 가정하면 안 된다. 동일한 base model, 지원 아키텍처·adapter 형식과 양자화 호환성을 확인해야 한다. 변환이 필요한 경우 변환 이미지/버전·출력 digest를 남기고 **실제 서빙 형식으로 다시 평가**한다. 현재 Qwen3 QLoRA 결과와 BGE 계열 학습 결과의 구체적인 추론 경로는 실측 검증 대상으로 둔다. [Ollama 모델 가져오기](https://docs.ollama.com/import)

## DAG와 실행 제어

기존 외부 제출·deferral 구조를 확장한다. UI와 API는 요청 검증·기록·조회, Airflow는 단계와 의존성 제어, 선택한 실행기는 학습·배치 평가·변환·재임베딩을 맡는다. 모델 가중치와 전체 데이터는 API 서버, DAG 파싱, XCom에 올리지 않는다.

작업 템플릿은 연결 진단, 데이터 준비/검증, 기준선 평가, 학습, 패키징, 후보 평가, 인덱스 생성, 서비스 적용으로 구분한다. 모든 실험에 모든 단계를 강제하지 않는다. 같은 환경·작업 템플릿의 DAG를 재사용하고 실행 입력으로 실험/모델 버전을 지정한다. 모델 하나 또는 실행 한 번마다 DAG 파일을 만들지 않는다.

현재 `model-lab`, `mlops`, `environment`, `backend`, `workload`, `contract`, `config` tags를 유지하고 프로젝트와 템플릿 버전을 추가한다. 요청은 `project_id`, `experiment_id`, `run_id`, 고정된 입력 manifest를 참조한다. DAG 배포는 writable 설치의 관리 경로와 Git/bundle 배포를 지원하고, 게시 완료와 DAG processor 반영 완료를 구분한다.

화면에서 실행하면 영구 Run을 먼저 만들고 DAG 제출 결과를 연결한다. PostgreSQL 기록과 Airflow API 호출 사이의 실패는 동일 요청 ID 조회·재연결로 복구한다. 후속 자동 제출이 필요하면 기존 Airflow 인증 규약에 맞는 서비스 권한을 설계하고 사용자 액세스 토큰을 작업 데이터에 저장하지 않는다.

실제 GPU를 사용하는 단계가 Pool을 점유하며 대기 중에도 필요한 점유를 유지한다. 가벼운 결과 집계와 CPU 전처리를 GPU Pool에 묶지 않는다. 자식 GPU 작업을 기다리는 조정 태스크가 같은 GPU Pool을 먼저 점유해 교착 상태를 만들지 않도록 한다. [Airflow deferral과 Pool 점유](https://airflow.apache.org/docs/apache-airflow/stable/authoring-and-scheduling/deferring.html)

현재 제공 워커의 추론 예약은 협약에 참여하는 요청만 제어한다. 같은 GPU를 사용하는 기존 챗봇 요청까지 자동 통제한다고 가정하지 않는다. 공유 자원 그룹의 모든 참여자에게 admission을 적용하거나, 학습 시간대·전용 GPU·추론 제한 정책으로 실제 경합을 해소해야 한다. 서로 다른 장비에는 전역 단일 잠금을 적용하지 않는다.

## 실행 상세와 실패 복구

실행 상태, 품질 판정, 서비스 적용 상태를 분리한다.

- 실행: 제출 대기 / 자원 대기 / 실행 중 / 취소 요청 / 취소 완료 / 완료 / 실패 / 상태 확인 필요.
- 품질: 평가 미실시 / 검토 대기 / 기준 충족 / 기준 미달.
- 적용: 미적용 / 적용 중 / 적용 확인 / 되돌림 / 적용 실패.

평가 프로세스가 정상 종료했어도 품질 기준은 미달할 수 있다. UI는 두 사실을 모두 보여준다. 학습 단계의 완료가 배포 허가가 되지 않는다.

| 상황 | 권장 동작 |
|---|---|
| 새로고침·탭 이동·브라우저 종료 | 실행은 계속되고 같은 Run 상세에서 다시 조회 |
| API 응답을 잃음·실행 버튼 재시도 | 같은 요청 ID로 기존 DAG/job 연결, 중복 학습 방지 |
| 자원 부족·quota·이미지 pull 대기 | 어떤 단계에서 기다리는지 표시. 입력 초안과 검사 결과 보존 |
| 외부 통신 단절 | 즉시 학습 실패/취소 완료로 단정하지 않고 마지막 확인 시각과 재조회 상태 표시 |
| 취소 요청 | 외부 실행 중단을 확인한 뒤 취소 완료. Airflow mark/clear와 외부 취소를 혼동하지 않음 |
| 재실행 | 기존 결과를 덮어쓰지 않고 새 attempt 생성. checkpoint 재개는 학습기 지원과 호환성 확인 후 수행 |
| 산출물 업로드 실패 | 학습 완료와 산출물 게시 실패를 구분하고 완전한 manifest만 후보 등록 |
| 품질 기준 미달 | 회귀 사례와 다음 개선 경로 제공. 운영 버전은 그대로 유지 |
| 적용 실패 | 현재 서비스가 사용하는 실제 버전을 재확인하고 이전 호환 구성으로 되돌림 |

실행 상세는 단계 타임라인, DAG/외부 job 링크, 요약 지표, 학습 곡선, 로그 참조, 산출물, 요청자·버전을 제공한다. 실행기마다 loss가 없으면 “미제공”으로 표시한다. 고빈도 원시 로그를 메타 DB에 계속 쌓기보다 외부 파일에 저장하고 UI용 요약만 제한적으로 기록한다.

장애 복구는 저장된 외부 job ID로 상태를 대조하는 과정이 필요하다. API 장애 중 파일 receipt는 복구 근거가 될 수 있지만 별도 SQLite를 운영 상태 저장소로 다시 만들지는 않는다. 서비스 적용 완료는 DB 별칭 수정만으로 확정하지 않고 대상 서비스의 상태를 확인한다.

## 현재 프로젝트에 적용하는 순서

1. **현재 평가 자산을 먼저 정리한다.** [Golden QA](../datasets/evaluation/README.md)는 LLM 16, 검색 12, DW 6, 고정 근거 답변 6의 총 40개 초안이다. `review_required`/`awaiting_data`를 완료된 정답처럼 점수화하지 않는다. 현재 holdout이 없으므로 확정된 일반화 성능도 주장하지 않는다.
2. **질문 해석·생성 기준선을 만든다.** 현재 챗봇의 Gemini 경로와 로컬 Qwen 후보를 프로젝트 평가 어댑터로 비교한다. [QueryPlan](../apps/chatbot/app/schemas/query_plan.py)의 의도·배우·기간·필터를 의미 단위로 채점한다. 모델 단독 테스트와 실제 LangGraph 경로의 평가는 분리한다.
3. **검색 기준선을 만든다.** 구조화 필터·인물 별칭·출연 관계 조회와 BGE-M3 의미 검색을 구분한다. 배우 출연작 전체 조회를 임베딩 Top-K 하나로 해결하도록 만들지 않는다. 실제 코퍼스 snapshot과 정답 ID가 준비된 사례부터 평가한다.
4. **RAG 전체 흐름을 평가한다.** 동일 데이터 snapshot에서 질문 해석 → 검색 → 근거 답변을 연결한다. 현재 6개의 가상 근거 답변 사례는 생성 단계 평가로만 사용한다.
5. **개선 원인에 맞춰 후보를 만든다.** 데이터/별칭/필터 문제는 해당 경로를 고친다. 표현·도구 사용·출력 계약 문제는 프롬프트나 모델 후보를 비교하고, 학습 필요성이 확인되면 train/validation을 준비한다. 평가 사례를 학습 파일로 자동 복사하지 않는다.
6. **작은 학습으로 실행 경로부터 검증한다.** 현재 로컬 control 워커의 RAM 6GiB와 미준비 학습 자산을 학습 가능 상태로 간주하지 않는다. 준비된 별도 실행 대상을 선택하거나 맞는 작은 학습기를 등록한다. GPU 진단 성공 뒤 실제 작은 학습·결과 등록·추론·재평가까지 한 번 이어지는지 확인한다.
7. **생성 모델과 검색 구성을 각각 적용한다.** Qwen 후보는 추론 형식의 호환성과 실제 챗봇 경로를 검증한 뒤 적용한다. BGE 모델/전처리를 바꾸면 해당 코퍼스의 새 인덱스와 질문 임베딩을 함께 전환하고 이전 묶음을 복구 가능하게 남긴다.

로컬 드라이브 경로, GPU 종류, 모델 이름은 [이 프로젝트의 실행 정책](local-model-storage.md)과 프로필에 둔다. 플러그인 공통 코드는 이를 기본 전제로 삼지 않는다.

## 구현 우선순위와 완료 조건

| 순서 | 구현 묶음 | 완료를 확인할 기준 |
|---|---|---|
| 1 | 프로젝트 프로필·추론 연결·공통 Run·역할 구분 | 서로 다른 두 프로젝트/추론 연결을 코드 수정 없이 선택. 기록 접근 분리. 새로고침 뒤 같은 실행 추적. 독립 자원은 병렬, 공유 자원은 경합 방지 |
| 2 | 데이터/평가셋 버전·일괄 평가·기준선/후보 비교 | 현재 프로젝트의 검토 완료 사례를 반복 실행하고 누락/실패 분모를 포함한 사례별 비교. 범용 예제 프로젝트에도 동일 동작 |
| 3 | capability 기반 학습 폼·산출물 등록·추론 패키징 | 준비된 외부 환경에서 작은 실제 학습 → 모델 버전 → 추론 → 같은 평가셋 비교. 지원하지 않는 조합은 제출 전 차단 |
| 4 | 인덱스 생성·서비스 적용·되돌리기·관측 | 테스트 서비스에서 모델/검색 묶음 전환과 복구. 외부 적용 실패 시 실제 사용 버전 확인 |

첫 두 묶음이 갖춰지면 학습 없이도 유용한 공용 Model Lab이 된다. 세 번째가 끝나면 모델 개선 과정이 연결된다. 네 번째가 끝나야 운영 적용까지 포함하는 MLOps 흐름으로 평가할 수 있다.

별도 검증 축은 HTTP와 Kubernetes의 실제 실행, API/triggerer/실행기 재시작, 제출 직후 응답 유실, 취소 중 통신 단절, DAG bundle 반영 지연, 미지원 학습기, 다른 Auth Manager와 Airflow 버전이다. 기존 계약 테스트와 실제 GPU 진단만으로 이 범위까지 검증되었다고 간주하지 않는다.
