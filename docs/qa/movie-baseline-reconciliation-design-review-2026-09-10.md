# 영화 기준선 대사 설계 선검토

판정: CHANGES REQUESTED. 읽기 전용 대사를 먼저 수행하고 업무 데이터 변경을 분리한 방향은 타당하다. 다만 아래 식별자 관계와 분류 계약을 확정해야 구현 결과를 일관되게 해석할 수 있다. 이번에는 설계와 관련 소스만 읽었으며 실데이터 실행이나 업무 코드 변경은 하지 않았다.

## 1. [P1] 원천 ID 브리지의 grain과 KMDb 공유 허용이 모순됨

대상: §6.1, §6.2.

`source_system × source_entity_type × normalized_source_id`당 한 행이며 각 행이 movie_key 하나를 가리키면, 같은 KMDb ID를 서로 다른 통합 영화에 연결할 수 없다. 반대로 해당 ID에 UNIQUE를 두지 않고 여러 행을 허용하면 선언한 grain을 위반한다. 여러 KOFIC ID가 같은 통합 영화를 가리키는 경우와, 하나의 KMDb 엔터티가 여러 통합 영화에 연결되는 경우를 구분해야 한다. 현재 서비스에 KMDb UNIQUE가 없다는 사실은 후자의 의미적 정당성을 입증하지 않는다.

구현 전 선택안: 원천 엔터티는 source tuple당 한 행으로 보관하고, 영화 연결은 별도 관계 또는 후보/검수 모델로 분리한다. 1:N이 필요한 경우 관계 grain에 movie_key와 관계 유형을 포함하고 허용 조건을 정한다. KOFIC 확정 연결은 한 시점에 movie_key 하나라는 제약을 유지한다. 공유 KMDb ID는 우선 충돌/검수 대상으로 집계하고 자동 확정하지 않아도 된다.

또한 두 bridge 모두 ‘ID당 한 행’과 ‘유효 시작·종료/이력 유지’를 동시에 제시한다. 현재 연결 테이블과 이력 테이블을 나눌지, 버전 행 grain을 둘지 정하고 활성 연결 유일성·유효기간 중첩 금지·병합/분리 시 이전 키 보존 방식을 명시해야 한다. 지금 DDL을 만들 필요는 없지만 후속 계약에는 결정이 필요하다.

## 2. [P1] 분류가 완전하고 상호 배타적이지 않아 입력 총건수 대사를 보장하지 못함

대상: §3, §4, §7.

‘유효 KOFIC ID’의 문법이 없고 잘못된 ID 분류가 없다. 서비스의 NOT NULL/UNIQUE는 공백 문자열이나 정규화 후 충돌까지 막지 않는다. legacy_only/service_only에는 중복을 제외한다는 규칙도 없어 한쪽에만 있는 중복 ID가 두 분류에 포함될 수 있다. 레거시 두 행과 서비스 한 행이 같은 ID일 때 서비스 한 행이 어느 집계에 들어가는지도 불명확하다.

필수 보완:

- ID는 문자열로 처리해 선행 0을 보존하고 trim, 허용 문자/길이, 대소문자 처리 규칙을 명시한다. 외부 원천의 유효성 검증과 단순 비교용 형식 검증을 구분한다.
- 양쪽에 missing/invalid/normalized-duplicate 진단을 둔다. 현재 서비스 제약상 missing이 없어야 하더라도 입력 검증에서는 빠뜨리지 않는다.
- ID별 양쪽 multiplicity를 먼저 계산하고, 어느 쪽이든 중복이면 해당 그룹의 모든 행을 ambiguous로 격리한다. 1:1인 경우에만 matched 필드 비교를 수행한다.
- 행 단위 배타적 분류와 ID 그룹 단위 진단을 구분하고, 각 원천의 배타적 행 수 합계가 원본 행 수와 같다는 식을 정의한다. 중복 ‘ID 수’와 ‘행 수’를 별도로 표시한다.
- 값 비교는 equal/conflict/left_only_value/right_only_value/both_missing/invalid 등으로 구분한다. 날짜·정수·boolean 파싱 실패를 null과 합치지 않는다. 배열/텍스트 hash에는 필드별 정규화·순서 보존·알고리즘 버전을 둔다.

필수 테스트에는 양쪽 중복, 한쪽 중복+상대편 단일 행, invalid ID, 정규화 충돌, invalid date/boolean, 분류 보존식을 추가한다. 기존 transform_legacy_snapshot은 중복 canonical key에서 즉시 실패하므로 중복 진단의 선행 입력 검증으로 그대로 사용하면 안 된다. 체크섬 검증과 행 진단을 분리해야 한다.

## 3. [P2] 기준선 채택 범위를 판단할 연도·정책·서비스 보존 대사가 빠져 있음

대상: §1, §2.2, §4, §7. 상위 승인 문서의 단계 0과 §7은 대상 연도·정책 차이까지 포함한다.

ID 교집합과 필드 충돌만으로 정책 적격 4,320건을 기준선으로 삼았을 때 어떤 기존 서비스 영화가 제외되는지 판단할 수 없다. 운영자 소유 테이블의 존재/행 수만으로는 해당 영화의 보정·논리 삭제·카테고리 관계가 보존되는지도 알 수 없다.

대사 집합별로 개봉연도/날짜 미상, 동일 정책 버전의 적격 여부·제외 사유, 서비스 공개·승인·논리 삭제 여부를 집계하고, 특히 service_only 및 정책 제외 그룹에 기존 공개 영화가 몇 건인지 확인해야 한다. editorial/미디어/카테고리 등의 관계는 개인정보 없이 movie ID 기준 연결·고아 행 집계로 보존 영향을 확인할 수 있다. 상세 보정 텍스트를 출력할 필요는 없다.

Gold 118건 연결을 목적에 포함하면서 v1 선택 사항으로 둔 것도 범위를 명시해야 한다. 선택 입력 없이 실행할 경우 결과는 ‘legacy↔service 대사 완료’까지만 판정하고 최신 API/Gold와의 기준선 통합 계약 완료로 표현하지 않는다. Gold 연결을 확인하려면 단순 총건수 요약이 아니라 ID 집합과 publication 식별자가 필요하다.

## 4. [P2] 현재값 상태의 출처와 매칭 변경 시 유지 범위를 명시해야 함

대상: §5.

source_observed_at과 ingested_at 분리, 네 가지 값 상태, 빈 값을 자동 삭제로 보지 않는 원칙은 적절하다. 다만 현재 상태표만으로는 KMDb 후보가 바뀌었을 때 이전 후보의 줄거리/포스터를 계속 유지해도 되는지 판단할 수 없다. ‘미수집’과 ‘이전 연결이 잘못되어 폐기됨’은 다르다.

각 필드 관측에 source entity ID, 매칭 결정/규칙 버전, 값 상태, 관측시각과 시각 근거를 연결해야 한다. 보류 시 이전 **유효한 확정 연결**의 값을 유지할 수 있는 조건과 연결 취소/오매칭 확정 시 무효화 조건을 구분한다. EXPLICITLY_CLEARED는 해당 필드의 권한 있는 원천과 명시적 삭제 증거가 있을 때만 허용한다. 파싱 오류는 PRESENT로 넣거나 삭제로 해석하지 않고 별도 오류로 기록한다.

실행할 병합 알고리즘은 이번 비목표로 유지해도 된다. 다만 같은 필드의 알려진/미상 시각, 동일시각 상충 값, source 우선순위를 판정할 계약 표 또는 미결정 상태를 결과에 남겨야 ‘현재값 계약 확정’이라는 완료 조건을 충족할 수 있다.

## 5. [P2] 읽기 전용과 재현성 경계를 실행 절차로 구체화해야 함

대상: §2.2, §2.3, §8.

기존 연결 재사용과 출력 제한 방향은 수용한다. 다음을 명시하면 구현자의 임의 선택을 줄일 수 있다.

- S3 입력은 정확한 manifest key와 해당 manifest가 지정한 객체로 고정한다. SUCCESS 문자열만 확인하지 말고 schema/status/bucket/key/bytes/SHA-256/record_count를 검증한다. 여러 manifest가 있으면 임의 latest를 선택하지 않는다.
- PostgreSQL은 첫 조회 전에 READ ONLY와 REPEATABLE READ를 적용한 단일 트랜잭션에서 영화 및 관련 집계를 읽는다. 원천 DB/스키마와 추출시각, S3 digest, 비교 규칙 버전을 결과에 기록한다. 서로 다른 저장소를 동일 시점 snapshot이라고 부르지 않는다.
- SQL은 고정 SELECT와 필요한 열만 사용한다. Airflow 연결은 읽기 조회만 하며 사용 자격증명의 권한 자체가 읽기 전용이라고 가정하지 않는다.
- stdout의 JSON 결과, stderr의 비밀 제거 오류 메시지, 허용 출력 필드를 정의한다. raw SDK 예외/DSN/Connection extras를 그대로 기록하지 않는다. `.local` 산출물은 명시적으로 제외·보호되는 위치인지 확인하고 결과 JSON에도 원천 전체 행을 넣지 않는다.

추가 사용자 승인 절차를 요구하는 지적은 아니다. 이미 승인된 읽기 전용 대사를 코드가 정확히 지키게 만드는 구현 계약이다.

## 수용하는 부분과 다음 검토 조건

순수 계산 모듈/외부 I/O 어댑터 분리, 제목만으로 자동 결합 금지, 임시 legacy observation key 사용, source_hash 알고리즘 차이 인정, 서비스 소유 필드 보존은 타당하다.

위 다섯 항목의 분류 규칙·관계 grain·최소 집계·출처 상태·실행 경계를 설계에 반영하면 구현 선검토를 다시 할 수 있다. 범위를 확장해 실제 적재나 서비스 DB 갱신을 할 필요는 없다.
