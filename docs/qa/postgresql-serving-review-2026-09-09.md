파일 대조 결과 `orchestration/airflow/dags`에는 현재 환경검사용 `pop_talk_environment_check.py`가 있고, `movie_sample_e2e`는 아직 확인되지 않았다. Airflow README는 별도 `airflow` DB/사용자와 서비스 `pop_talk_local` DB를 분리한다고 명시한다. 따라서 아래의 테이블 18개는 **서비스 DB에 대한 전수 목록**이며 Airflow 메타 DB까지 포함한 인스턴스 전체 목록이 아니다.

이 문서의 P1/P2는 **해당 기능을 서비스 완료로 판단하기 전에 해결할 중요도**다. 현재 개발 단계에서 전부 장애가 발생했거나 다른 작업이 실패했다는 의미는 아니다. 분류를 다음과 같이 보정한다.

- **확인된 현재 결함:** 관리자 직접 쓰기의 검증/감사 우회, 공개 조건 차이, 로그인 실패 카운터 롤백, 현재 게시 코드의 부분 컬럼 UPSERT. 조회 시점의 코드에서 여전히 확인되며 다른 두 작업의 최근 수정 범위는 주로 Airflow/모델이다.
- **진행 단계상 남은 통합:** DW 게시본 → 앱 메타데이터 승격, 분석 마트 → 대시보드, 전체 영화 BGE-M3 재생성 → 챗봇, 실제 E2E DAG. 미구현이라는 사실은 유지하되 중복 구현을 시작할 대상은 아니다.
- **개선 후보:** 출처별 평점 요약, 문구 카운트 쿼리, 관계 배열의 정규화, 필요한 인덱스. 기존 실측은 검토 시점 데이터의 기준선이며 병행 실행 중인 장비의 성능 SLA로 사용하지 않는다.

권장 작업 경계는 DW 작업이 수집·Airflow·dbt·게시를, 모델 작업이 Ollama·모델 무결성·추론 검증을 진행하고, 서비스 DB 검토에서는 두 흐름을 연결할 **키·소유 컬럼·공개 조건·게시 버전·임베딩 버전 계약**을 정리하는 것이다. 이는 배정이나 다른 세션에 대한 지시가 아니라 충돌을 줄이기 위한 제안이다. 기존 P1의 DW 연결 항목은 아래에서도 이 보정과 함께 읽는다.

이번 추가 확인에서는 클라우드 작업과 모델 테스트를 재실행하지 않았다. 성공/진행 보고는 해당 세션 기록을 근거로 하며, 완료된 것으로 표시하려면 실제 반영 코드·DB와 검증 결과를 다시 대조해야 한다.

## 1. 판단

PostgreSQL을 **사용자 서비스의 트랜잭션 원장 + DW 결과를 빠르게 읽는 서빙 DB**로 사용하는 방향이 적절하다. 영화·리뷰·회원의 현재 규모에서는 DB 분산이나 모든 속성의 정규화보다, **누가 어떤 값을 쓰는지와 모든 화면이 어떤 기준으로 읽는지를 통일하는 일**이 먼저다.

현재 구조의 좋은 점은 영화 BIGINT 키와 사용자 UUID 키를 참조 관계로 연결하고, 영화 원본과 관리자 줄거리 보정을 분리하며, 미디어·벡터·작업 큐를 별도 테이블에 둔 것이다. 리뷰 평점 CHECK, 회원별 영화 리뷰 중복 방지, 리프레시 토큰 해시, 큐의 활성 작업 중복 방지와 lease도 유지할 가치가 있다.

그러나 아직 하나의 완결된 서비스 데이터 흐름은 아니다. DW 게시 결과는 앱에 연결되지 않고, 관리자와 WAS가 같은 테이블을 서로 다른 규칙으로 수정하며, 사용자·챗봇이 서로 다른 공개 조건과 줄거리를 읽는다. 성능상으로는 리뷰·카테고리 집계를 요청마다 반복하는 부분부터 줄이는 것이 합리적이다.

검토만 수행했다. 서비스 코드·테이블·데이터·인덱스는 변경하지 않았다. 추가 파일은 이 보고서와 읽기 전용 감사 근거다.

## 3. 우선순위별 발견 사항

### P1 — 관리자 DB 직접 쓰기가 WAS의 규칙과 감사를 우회

`apps/admin/src/lib/db.ts`는 서버에서 직접 PostgreSQL에 연결하고, `app/admin-api/movies/[id]/approval/route.ts`는 `body.admin` 문자열을 받아 원장에 UPDATE한다. 이 경로에는 인증·역할 검증과 `admin_audit_logs` 기록이 없다. 반면 `apps/was/app/admin.py`는 `require_admin`과 감사 기록을 사용한다. 브라우저에 DB 연결 문자열이 내려간다는 뜻은 아니며, **관리자 Next.js 서버가 별도 백엔드처럼 동작한다는 문제**다.

동일한 반려 동작도 WAS는 HIDDEN으로 바꾸지만 관리자 직접 경로는 승인 상태만 바꾼다. 현재 DB에는 `PUBLISHED/REJECTED` 1건이 있다. 어떤 경로가 이 행을 만들었는지는 이번 읽기만으로 확정하지 않는다.

권장: 관리자 화면의 `/admin-api`를 인증된 WAS 호출용 중계로 전환하고, 쓰기·검증·감사를 WAS에 모은다. 감사 actor는 요청 문자열이 아니라 인증된 users.id를 사용한다. localhost 실행이라는 현재 환경과 서비스용 접근 제어 완성 여부는 구분한다.

### P1 — 노출·인증·정책 조건이 서로 다름

`apps/was/app/public_catalog.py:96`은 `is_removed=false`만 확인한다. DRAFT 10건도 공개 목록 대상이다. 챗봇은 `service_status='PUBLISHED'`를 요구하고 임베딩 트리거는 추가로 APPROVED를 요구한다. WAS의 노출 API 역시 APPROVED를 요구하지만 관리자 화면 설명은 노출과 인증이 독립이라고 한다.

인증을 배지로 사용할지 게시 필수조건으로 사용할지부터 한 규칙으로 결정해야 한다. 코드와 관리자 문구를 보면 **노출은 service_status, 검수 배지는 approval_status로 독립 관리**하는 설계가 자연스럽다. 이 안에서는 미인증 공개 영화도 검색 문서 생성 대상이 되어야 한다. 검수 완료만 공개하는 정책을 택한다면 모든 쓰기·조회·큐 조건에서 함께 강제해야 한다.

또한 2020년 이전 개봉 영화 570건 중 568건이 PUBLISHED다. 프로젝트의 연도·제외 정책은 현재 서비스에 일관되게 적용되지 않았다. 원본을 삭제하지 말고 `policy_eligible`과 제외 이유/규칙 버전을 게시 결과에 보존한다. 재개봉 예외는 확정된 정책이 아니므로 제작연도로 임의 제외하지 않는다.

권장 공통 공개 조건: `service_status=PUBLISHED AND NOT is_removed AND policy_eligible`. 인증 필수 정책을 택할 때만 APPROVED를 추가. 영화 상세·목록·추천·영화별 리뷰 읽기/쓰기 모두 같은 조건을 사용한다. 현재 공개 리뷰 목록은 영화 공개 여부 자체를 확인하지 않는다(`reviews.py:66`).

### P1 — DW 성공이 실제 서비스 갱신을 의미하지 않음

`publish_to_postgres.py`는 `dw_serving.movie_catalog`에만 쓰고, 사용자 API·관리자·챗봇은 `dev.popcorn_movies` 계열을 읽는다. 코드 검색에서 앱이 dw_serving을 사용하는 경로는 확인되지 않았다. 게시된 100건은 KOFIC 코드로 기존 영화와 모두 연결되지만 영구적인 연결 계약·FK는 없다.

지금은 기존 로컬 데이터 → DW 실험 → 별도 100건 게시 확인 단계다. 이를 사용자 대시보드까지 연결 완료한 것으로 보기는 어렵다. MVP 영화 카탈로그에는 `source_keywords` 등 현재 추천·자동 분류에 필요한 일부 필드도 빠져 있어 기존 API 원본을 그대로 대체할 수 없다.

권장: 기존 `popcorn_movies.id`를 유지하고, DW 통합 키와 이 ID를 명시적으로 연결한다. 검증된 영화 게시본을 서비스 메타데이터로 승격하는 경로를 하나 만든다. 그 과정에서 사용자 리뷰·운영 보정·승인·노출은 건드리지 않는다. 원천 배치와 Reverse ETL이 같은 원천 컬럼을 동시에 소유하지 않도록 최종 writer를 하나로 정한다.

### P1 — 게시 재실행 시 해시와 실제 내용이 어긋날 수 있음

`publish_to_postgres.py:249`의 staging 충돌 갱신은 해시·제목·개봉일·시각만 바꾼다. 같은 run_id의 줄거리·배우가 바뀌면 해시는 새 값인데 내용은 이전 값으로 남고, 그 내용이 다시 게시된다. 최종 카탈로그 충돌 갱신도 KOFIC/KMDb ID·movie_type·source_system 등의 정정을 누락한다.

권장: 같은 run_id는 불변 입력 체크섬으로 잠그고 내용이 달라지면 새 run을 발급하거나, 재시도 시 해당 실행 staging을 검증 가능한 전체 내용으로 교체한다. 최종 UPSERT도 컬럼 소유권 표에 있는 모든 원천 필드를 일관되게 갱신한다.

RUNNING 삽입과 SUCCESS가 하나의 트랜잭션 안에 있고 FAILED 기록 경로는 없다. 실패 시 이력도 롤백되어 운영 화면에서 실패를 관측할 수 없다. 시도 이력은 별도 짧은 트랜잭션으로 남기고, 실제 게시와 활성 버전 교체만 원자적으로 수행한다. 현재 단일 트랜잭션이 부분 적재 노출을 막는 장점은 유지한다.

현재는 UPSERT만 하므로 게시 대상에서 빠진 영화가 자동으로 제외되지 않는다. 전체 스냅샷인지 증분인지 명시하고, 전자는 해당 소스의 누락 키 처리, 후자는 명시적인 tombstone으로 서비스·검색 제외를 전달한다. 오래된 run이 최신 값을 덮어쓰지 못하도록 버전 순서 검증도 필요하다.

### P2 — 보정 줄거리와 카테고리가 소비자마다 다르게 반영

사용자 API는 보정 줄거리를 적용하지만 실 DB의 `popcorn_movies_service`는 원본 plot만 제공한다. 관리자 직접 조회와 챗봇은 이 뷰를 읽으므로 WAS로 보정을 저장해도 서로 다른 내용을 보여주게 된다. 현재 editorial은 0건이라 기존 데이터에서 이미 잘못 보인 사례를 확인한 것은 아니다.

관리자는 `match_keywords && source_keywords` 자동 분류와 수동 링크를 보여주는데 공개 API의 curated_categories는 수동 링크만 읽는다. 현재 링크가 0건이므로 사용자 API의 운영 카테고리는 비어 있다. 자동 분류를 사용자 서비스에서도 쓰려면 공통 effective category 조회를 정의하고 출처를 함께 제공해야 한다.

권장: 보정된 영화 기본값을 내는 가벼운 뷰와 공개 대상 뷰를 만든다. 기존 관리자 뷰 이름을 즉시 공개 전용으로 바꾸면 관리자 검수 대상이 사라질 수 있으므로 용도를 나눈다. 미디어 전체 JSON과 운영 진단 정보는 상세용으로 분리한다.

### P2 — 평점 출처 혼합 및 반복 집계

현재 리뷰는 LOCAL 6,643건, naver_movie 118,301건이며 모두 ACTIVE 상태다(삭제 여부를 제외한 상태별 집계). 챗봇 `get_rating_stats`는 출처별 필터를 쓰지만 `recommend_movies`/`find_serendipity_movie`는 출처 구분 없이 평균을 낸다. 같은 영화라도 상세 답변과 추천의 평점 기준이 달라진다. 관리자 리뷰 총계는 외부 리뷰까지 세면서 카드에 “사용자 작성”이라고 표시한다.

권장: `영화 × 출처`별 요약을 기준으로 평균·평가 수·기준일·원래 척도를 함께 제공한다. 무평점은 null/0건이며 0점으로 표시하지 않는다. 최소 평가 수 조건을 명시한다. 외부 평점 전체를 사용자 평점과 섞어 단일 점수로 제시하려면 별도의 점수 정의가 먼저 필요하다.

### P2 — 중앙 마이그레이션으로 현재 DB를 재현하지 못함

README도 users/reviews 등의 최초 DDL이 없다고 명시한다. 실 DB display_categories에는 short_label/category_codes가 있고 예전 code/axis 기반 모델과 다르며, movie_categories에는 match_keywords 및 SITUATION 유형이 있다. 이 상태와 현재 뷰 전체를 중앙 001~015만으로 재현할 수 없다. 게시용 DDL은 Python 안에 따로 있다.

권장: 현재 스키마를 기준 baseline으로 고정하고 이후 변경만 순번·체크섬 이력으로 관리한다. 적용 이력이 불명확한 DB에 과거 migration 전체를 재실행하지 않는다. 새 DB 재현 검사에서 뷰·함수·트리거·도메인까지 대조한다. `queue_movie_embedding`/`protect_removed_movie`의 무스키마 참조도 대상 스키마에 고정한다. admin의 dev 하드코딩에만 의존하지 않는다.

### P2 — 관계를 배열로 보관해 참조 무결성에 빈틈

users.onboarding_movie_category_ids와 display_categories.category_codes는 FK가 없다. 현재 고아 참조는 둘 다 0건이지만, WAS 카테고리 삭제는 movie_category_links만 검사하므로 사용자의 취향이나 화면 문구가 참조 중인 분류도 삭제될 수 있다. 단순 읽기 중 누락 항목을 숨기는 것으로 해결되지 않는다.

권장 관계 테이블: `user_category_preferences(user_id, category_id)`와 `display_category_rules(display_category_id, category_id, sort_order)`. PK/FK를 두고, 선택 수 제한은 WAS에서 검증한다. API 응답은 계속 배열로 제공할 수 있어 FE가 DB 정규화 구조를 알 필요는 없다. 당장 테이블을 늘리지 않는 단계에서는 hard delete를 막고 비활성화만 허용하는 것이 간단하다.

### P2 — 로그인 실패 카운터가 예외와 함께 롤백

`apps/was/app/auth.py:76–87`은 transaction 안에서 실패 횟수를 올린 뒤 ProblemError를 던진다. 따라서 users에 준비된 잠금 컬럼이 정상 작동하지 않는다. 이번 검토에서는 쓰기 테스트를 반복하지 않았으며, 같은 프로젝트의 앞선 통합 검토 문서에도 재현 결과가 기록돼 있다. 실패 상태를 커밋한 다음 401/429를 반환하도록 경계를 고쳐야 한다.

## 4. 성능 실측과 개선 순서

로컬 DB에서 `BEGIN READ ONLY`, `statement_timeout=20s`, `EXPLAIN (ANALYZE, BUFFERS)`를 사용했다. 아래는 쿼리 구조를 대표하는 축약 SELECT의 단일 실행 값이다. HTTP·직렬화·LLM·동시 부하 시간은 제외되며 운영 p95가 아니다.

| 대표 조회 | 실행 시간 | 관측과 조치 |
|---|---:|---|
| 영화 20건 + 전체 개수 window | 4.579ms | 현재 빠름. 5,319행 처리하므로 무한 스크롤에는 count 생략·cursor 적용 여지 |
| 제목 부분검색 | 2.035ms | 현 규모에서 긴급 병목 아님. 규모 증가 시 검색 인덱스 검토 |
| 추천용 영화별 리뷰 평균 + 상위 10건 | 385.403ms | LATERAL 집계 5,309회 반복. 출처별 요약 또는 먼저 한 번 GROUP BY하는 쿼리로 전환 |
| 회원 전체 + 회원별 리뷰 수 | 1.930ms | 현재 기존 인덱스 사용으로 빠름. 전체 회원을 공통 layout에 내려보내는 구조는 성장 시 비효율 |
| 화면 문구 16건 + 영화 수 | 487.287ms | 문구별 영화 전수 비교. 관계를 한번 계산해 category별/문구별 집계 후 조인 |

첫 개선은 쿼리 형태다. 평점은 우선 `(movie_id, source_system)` GROUP BY 1회와 조인으로 바꾸고, 실제 부하에서 부족하면 요약 테이블을 도입한다. 카테고리는 일치하는 `(category_id,movie_id)` 관계를 한 번 계산하고, 문구별 영화 중복을 제거한 후 COUNT한다. 자동 분류 캐시를 만들 경우 카테고리 규칙 변경과 영화 키워드 변경 모두 갱신해야 한다.

admin RootLayout은 영화 300건·미디어·임베딩 상태·회원 전체·문구 집계·schema guard를 초기 로드한다. SQL을 병렬로 호출해도 불필요한 계산과 응답 크기가 사라지지는 않는다. 대시보드는 `/admin/dashboard/summary` 집계 응답을 받고, 목록/상세는 해당 화면에서 필요한 페이지·필드만 읽게 한다. schema guard는 시작 시나 짧은 TTL로 확인하고, DB 장애 시 mock을 실데이터처럼 섞지 않는다.

인덱스 후보는 실제 쿼리 변경 후 실행 계획으로 선택한다. 전부 추가할 목록이 아니다.

- 공개 영화: 공개 조건에 맞는 `(release_date DESC, id DESC)` 부분 인덱스. 연도·is_removed가 다른 테이블/뷰에 있으면 부분 조건에 그대로 넣을 수 없으므로 실제 컬럼 구조에 맞춰 설계한다.
- 리뷰: `(movie_id, source_system, created_at DESC, id DESC) WHERE deleted_at IS NULL AND status='ACTIVE'`를 출처별 목록에 맞춰 검토. 기존 인덱스와 중복 비용 비교.
- 제목: `%검색어%`에는 현재 title_ko B-tree만으로 충분하지 않다. 필요 시 pg_trgm GIN/GiST를 사용하되 짧은 한국어 검색어까지 시험한다. 추출 가능한 trigram이 없으면 효과가 제한된다. [PostgreSQL 17 공식 문서](https://www.postgresql.org/docs/17/pgtrgm.html)
- 배열: 기존 GIN을 살리려면 동등한 의미가 보장되는 곳에서 `= ANY(array)`보다 `&&`/`@>` 지원 연산을 검토한다. unnest 후 부분 문자열 검색은 기존 배열 GIN만으로 해결되지 않는다. [인덱스 유형 공식 문서](https://www.postgresql.org/docs/17/indexes-types.html)
- 벡터: 실제 HNSW/IVFFlat 인덱스가 없다. 5천 편 규모라는 이유만으로 즉시 추가하지 않는다. 먼저 모델·문서 일치와 평점 집계 비용을 해결한다. HNSW를 도입할 때 차원과 캐스트·연산자·ORDER BY를 인덱스 정의와 맞추고 필터 적용 시 recall을 검증한다. 인덱스 추가만으로 모든 결합 정렬이 빨라지지는 않는다. [pgvector 공식 문서](https://github.com/pgvector/pgvector)

페이지 범위를 벗어나면 `count(*) OVER()` 결과 행도 없어 total=0으로 돌아가는 API가 여럿 있다. 정확한 total이 필요한 관리자 목록은 별도 COUNT 응답을 사용하고, 사용자 스크롤은 cursor/has_more 계약을 권장한다. 날짜 조건은 컬럼을 `::date`로 가공하기보다 명시한 시간대의 시작 이상·다음날 시작 미만 범위를 전달한다.

## 5. 권장 최종 데이터 흐름

```text
외부 API / 파일 / 외부 평점
  → 원천 보관 → Databricks 정제·매핑 → Snowflake + dbt 검증·집계
  → PostgreSQL 실행별 staging 검증
      ├─ 영화 메타데이터 승격 → 기존 popcorn_movies ID 유지
      └─ 분석 요약 게시 → dw_serving의 화면용 집계 테이블

사용자 FE → WAS → users / reviews / preferences
관리자 FE → 인증된 WAS → editorial / 분류 / 승인·노출 + audit
                          ↓
             보정·정책을 반영한 공통 영화 조회
                  ├─ WAS → 사용자·관리자 화면
                  └─ 변경 해시 → 기존 임베딩 큐 → 로컬 워커 → 벡터
                                                              ↓
                                    챗봇 → 공통 영화 + 출처별 집계 + 벡터

서비스 리뷰 변경 → 증분 추출 → DW 분석 (필요한 분석에만)
```

회원가입·리뷰 작성·관리자 변경은 즉시 PostgreSQL에 반영한다. 이 작업을 Snowflake/dbt 완료까지 기다리게 하지 않는다. 반대로 외부 대량 평점과 장기 흥행 집계는 DW에서 계산하고 화면에서 필요한 결과만 게시한다. 실시간 변경과 배치 집계의 시간차는 API의 기준일로 설명한다.

영화 키는 내부 `movie_id`와 외부 출처 키를 분리한다. 현재 dbt의 `md5(ingestion_source|source_movie_id)`는 출처 레코드 키이지 여러 출처의 같은 영화를 통합하는 canonical 키가 아니다. DW의 통합 키를 확정하고 `(source_system, source_movie_key) → canonical_movie_key → popcorn_movies.id` 연결을 검증한다. 외부 ID는 앞자리 0·문자 가능성을 수용하는 문자열로 보관한다.

게시 항목별 소유권:

| 데이터 | 쓰기 주체 | 서비스 조회 |
|---|---|---|
| 영화 원천 제목·장르·출연진·개봉일·원본 줄거리 | 검증된 DW 게시 경로 | 보정된 서비스 뷰 |
| 승인·노출·관리자 보정·수동 분류 | WAS 관리자 기능 | 동일 서비스 뷰 및 관리자 전용 조회 |
| 회원·취향·자체 리뷰 | WAS 사용자 기능 | 저장 직후 조회 |
| 외부 평점·흥행·데이터 품질 요약 | dbt 게시 | dw_serving 요약 조회 |
| 벡터 | 임베딩 워커 | 모델/문서 버전과 공개 조건을 확인한 챗봇 조회 |

|---|---|---|
| movie_source_links | 출처 영화 키 하나와 서비스 영화의 연결 | 중복 영화·잘못된 리뷰 연결 방지. DW 통합키 포함 |
| user_category_preferences | 사용자 × 카테고리 | 취향 FK와 삭제 정책 |
| display_category_rules | 문구 × 카테고리 | 화면 문구와 분류 관계 무결성 |
| movie_rating_summary | 영화 × 출처의 현재 요약 | 자체 평점 최신값; count/sum 또는 avg와 집계 시각 |
| dw_serving.movie_rating_snapshot | 영화 × 외부 출처 × 기준일 | DW 외부 평점 게시. native 척도·평가 수·매핑 범위 표시 |
| dw_serving.boxoffice_daily | 영화 × 집계일 × 관측 범위 | 일별 관객·매출. 누적 수치를 날짜별 합산하지 않음 |
| dw_serving.data_quality_results | 실행 × 대상 × 검증 항목 | 결측·미매칭·정책 위반·신선도 |
| 게시 manifest/활성 버전 | 데이터셋 × 게시 버전 또는 현재 포인터 | 여러 마트의 일관된 게시와 직전 정상본 유지 |

자체 리뷰 요약은 먼저 직접 GROUP BY로 제공해도 된다. 물리 요약이 필요해지면 자체 리뷰는 쓰기 트랜잭션에서 변경하거나 짧은 지연 갱신으로 처리하고, 외부 집계는 배치가 담당한다. 동일 요약 행을 WAS와 DW가 동시에 덮어쓰지 않는다.

API는 운영 현황과 DW 분석을 구분한다. 운영 현황에는 영화 노출/검수 수, 자체/외부 리뷰 수, 회원 상태 수, 최신 작업 상태를 제공한다. DW 분석에는 출처별 평점 추이·관측 범위가 있는 흥행·품질 항목을 제공한다. 응답에는 source_as_of, calculated_at, published_at, run_id, metric_version 등 실제 의미가 있는 메타데이터를 일관되게 제공한다. 현 게시 코드는 source_as_of를 source_synced_at으로 복사하므로 원천 기준일과 수집 시각을 구분할 수 없다. 시각은 원천 timezone 계약을 확인하고 timestamptz/UTC로 전달한다.

사용자 홈의 “팝톡 추천”은 현재 최신 카탈로그 30건에서 인증 영화를 고르는 방식이다. 이는 개인화 순위가 아니다. `/recommend` 페이지에는 정적 MOVIES 참조도 남아 있다. 이를 위해 막연히 추천 이력 테이블부터 추가하지 말고, 홈 최신/인증 목록과 개인화 추천 API를 구분한다. 개인화는 사용자 취향 + 공개 영화 + 출처별 평점 + 유효 벡터를 사용하고, 이후 평가 필요 시 추천 실행·노출 이력을 최소 형태로 기록한다.

## 7. 임베딩·운영에서 추가로 지켜야 할 계약

- DB에 BGE-M3 READY 5,308건이 있으나 모델 문자열만으로 실제 생성 모델을 증명할 수 없다. 복원 스크립트는 레거시 CLOVA 벡터라고 설명하고 과거 mock 주석도 이름 혼용을 언급한다. 이번 검토는 실제 BGE-M3 재생성 여부나 검색 품질을 검증하지 않았다. 모델 revision·생성 출처·차원·문서 해시를 확인한 후 검색에 사용한다.
- 기존 Compose에는 임베딩 워커 서비스가 없다. 큐 5,338건이 SUCCEEDED라는 과거 상태만으로 이후 변경이 자동 처리된다고 볼 수 없다. 기존 배치 워커를 이 프로젝트에 명시적으로 연결하고 재시도·lease 만료 복구를 검증한다.
- 처리 중 영화가 바뀌면 ON CONFLICT DO NOTHING으로 새 큐 항목이 생기지 않을 수 있다. 워커가 입력 해시와 최신 해시를 비교하고 재큐잉하는지 검증해야 한다. 워커의 동작을 보지 않고 변경 유실이 확정됐다고 단정하지 않는다.
- 카테고리 링크 변경뿐 아니라 이름·aliases·match_keywords·활성 여부 변경도 검색 문서에 영향을 준다면 재생성 범위에 포함한다. 메타데이터 갱신 때 모델 재생성을 동기 실행하지 않는다.
- 채팅은 같은 트랜잭션의 두 메시지가 동일 created_at을 가질 수 있지만 실제 messages.id는 BIGINT sequence여서 현재 `created_at,id` 정렬에 동률 해소 키가 있다. 별도 순서 테이블을 당장 추가할 필요는 없다. 새 세션 동시 생성 시 SELECT FOR UPDATE로 아직 없는 행을 잠글 수 없으므로 충돌 처리·재시도는 확인한다.
- 토큰·대화·완료 큐·staging 보존기간을 정하고 작업별로 정리한다. 현재 규모에서는 파티셔닝부터 시작할 이유가 없다. 별도 DB 역할로 WAS·챗봇·게시 워커의 쓰기 범위를 제한하되 현재 계정 권한 전수 감사는 이번 범위에서 수행하지 않았다.

## 8. 진행 순서와 완료 기준

1. **규칙/정확성:** 공개 조건·검수 의미·연도 정책·컬럼 소유권 확정, 관리자 쓰기 WAS 통합, 공통 보정 뷰, 로그인 실패 커밋 수정. 숨김 영화가 목록·상세·챗봇·리뷰에서 같은 결과인지 검증.
2. **게시 연결:** baseline과 마이그레이션 이력 정리, 영구 키 연결, 완전한 staging 갱신, 실패 기록, 오래된 run 방지, 메타데이터 승격 구현. 같은 배치 재실행·중간 실패·삭제 전파·운영 보정 보존을 검사.
3. **성능:** 출처별 평점 집계와 문구 카운트 재작성, 대시보드 summary API, 페이지별 데이터 조회. 동일 데이터·쿼리 의미로 실행 계획을 비교하고 결과 값이 같음을 확인.
4. **분석 화면:** 필요한 평점·흥행·품질 마트부터 게시. 기준시각·출처·관측 범위를 보여주고 로컬 마지막 정상본으로 시연 가능하게 함.
5. **검색 품질:** 실제 임베딩 모델 검증/재생성, 변경·삭제 전파, Golden QA 평가 후 벡터 인덱스 필요성 판단.

이번에 실행한 것은 스키마 전수 읽기·행 수/무결성 집계·대표 SELECT 5개의 실행 계획 측정이다. 운영 부하 테스트, 모든 API의 실행 테스트, 관리자 쓰기, DDL 적용, 외부 DW 재실행, 임베딩 생성은 수행하지 않았다.
