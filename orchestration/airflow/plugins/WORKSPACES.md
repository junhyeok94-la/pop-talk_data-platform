# 개인 업무와 운영 모니터링

## 메뉴의 역할

| 메뉴 | 대상 | 데이터와 저장 |
|---|---|---|
| 내 대시보드 · 담당 DAG | 담당자의 상태 확인·실패 처리 | 현재 Airflow DAG 권한 + PostgreSQL 집계, 계정별 담당 범위 |
| 내 대시보드 · 차트·추세 | 개인별 패널·쿼리·배치 | 기존 Studio와 계정별 저장 이력 |
| 운영 모니터링 | 팀이 완성한 공통 운영 화면 조회 | 관리자 등록 URL을 iframe으로 표시 |
| Model Lab | 평가·실험·외부 학습 오케스트레이션 | 프로젝트별 권한·DAG·외부 실행기 |

새 설치나 업데이트에는 기존 Airflow PostgreSQL에서
`PYTHONPATH=/opt/airflow/plugins python -m airflow_workbench.metadata`를 실행하고 API 서버를
재시작한다. 마이그레이션 6은 `workbench.dashboard_actions`를 추가한다. Airflow 기본 테이블이나
Alembic 버전을 변경하지 않는다. SQLite, 새 DB 계정, Grafana·Prometheus 설치는 필요하지 않다.

## 개인 담당 범위

최초 설정은 빈 범위이다. 업무 태그는 쉼표로 구분하고 여러 태그 중 하나라도 일치하면 포함한다.
직접 선택한 DAG도 함께 포함하며 현재 계정의 조회 권한으로 다시 제한한다.
직접 선택 최대 200개, 태그 최대 20개, 최종 담당 범위 최대 200 DAG를 지원한다.
한도를 넘으면 태그를 좁힌다. 다른 창에서 설정을 변경한 경우 버전 충돌을 알린다.

조회 기간은 화면에서 1·7·30일을 선택하고 장기 실행 기준은 분 단위로 지정한다.
성공 시각은 **조회 기간 안의 마지막 성공**이다. 과거 실패 실행은 나중에 같은 DAG가
성공했더라도 기록으로 남으므로 실행 날짜·데이터 범위를 확인한 뒤 조치한다.

담당 범위는 `documents`의 `work-profile:<서버가 결정한 소유자>`에 저장한다.
소유자는 Auth Manager 종류와 인증된 계정 ID로 결정한다. 요청에서 다른 계정의 owner를
지정할 수 없다. 기존 Studio 보드·쿼리·레이아웃·저장 이력은 별도로 유지한다.

같은 Profile 문서에 검색어·실행 상태·DAG 활성 여부·자동 갱신 간격을 저장한다.
스키마 추가 마이그레이션 없이 기존 문서에 기본값을 적용한다. `work/scope`와 `work/summary`,
Studio의 공유 모드는 서버의 `workspace()`로 담당 범위를 해석한다. 검색 단어는 AND이며
DAG ID·표시 이름·태그·소유자를 대소문자 구분 없이 검사한다. 검색은 최대 200개의 담당 DAG만
좁히며, 실행 상태 조건은 집계 이전에 적용한다. 마지막 성공 시각은 상태 필터와 독립적으로 유지한다.

Studio Context의 `follow_work_scope=true`가 기본이다. 이때 클라이언트가 보낸 기간보다
계정 Profile의 기간·상태를 우선하며, 집계 대상은 현재 권한과 담당 범위의 교집합이다.
캐시 키에는 실제 DAG 집합·상태·기간·패널 조건이 들어간다. 빈 담당 범위나 검색 결과는
전체 권한 범위로 대체하지 않는다. 다른 데이터소스는 이 모드에서 실행하지 않는다.
`follow_work_scope=false`는 화면에 명시되는 별도 분석으로, 기존 SQL·MLOps·보드 기간을 지원한다.
두 모드 모두 DAG·데이터소스 권한 검사는 유지한다.

공통 `dashboard/static/workspace.js`가 필터 적용·버전 충돌·토글·간격·아이콘 버튼을 제공한다.
두 페이지의 `dashboard-shell`에는 페이지 제목, 공통 필터, 탭 탐색을 순서대로 배치하며
탭별 본문 `#app`과 분리한다. 공통 필터가 탭 내부 조건으로 보이지 않도록 탭보다 먼저 표시한다.
두 탭의 `.dashboard`는 최대 폭 1680px, 좌우 여백 30px(1050px 이하 18px),
카드 간격 16px를 공유한다. 제목과 본문에 같은 폭 규칙을 적용하고 스크롤바 공간을 유지한다.
공통 필터 컨트롤은 높이 34px와 별도 스타일 범위를 사용해 Studio의 폼 스타일에 영향받지 않는다.
카드 제목은 44px 기준으로 세로 정렬하며, 패널 도구와 검색 초기화는 SVG 아이콘을 사용한다.
주기 조회와 수동 조회는 동일 API/캐시 경로를 사용하며, 수동 클릭으로 전체 캐시를 무효화하지 않는다.
혼잡하면 대시보드 갱신을 먼저 미루고 마지막 조회 시각·갱신 보류 안내를 표시한다.
조회 한도·DB/API 혼잡 감지·재시도와 배포 한계는 [운영 보호](DASHBOARD_PROTECTION.md)를 따른다.

## DAG 활성화와 일시중지

담당 DAG 영역의 **활성화 / 일시중지**는 native `PATCH /api/v2/dags/{dag_id}`의
`is_paused`를 사용한다. 확인 화면을 열 때 현재 상태와 DAG 변경 권한, 스케줄을 조회하며
요청 직전에 상태와 권한을 다시 검사한다. native API도 현재 사용자 권한을 검사하고 감사
로그를 남긴다. 상태가 바뀌었으면 다시 확인한다. 활성화에 따라 예약·catchup 실행이 시작될 수
있고, 일시중지가 실행 중인 태스크를 취소하지는 않는다. DAG 파일 미존재(`is_stale`)·파싱 오류의
해결은 별개이며, Model Lab 관리 DAG는 환경·연결 메뉴에서 처리한다.

## 실패 재실행

1. 실패 행에서 **재실행 대상 확인**을 누른다.
2. 현재 사용자의 native DAG/Run 조회 권한과 태스크 변경 권한을 검사한다.
3. `clearTaskInstances`를 `dry_run=true`로 호출하여 대상 태스크·매핑 인덱스·상태·시도를 보여준다.
4. 사용자가 메모와 함께 확인하면 현재 상태와 대상을 다시 조회한다. 미리보기 이후 바뀌었으면 중단한다.
5. `dry_run=false`로 정확한 태스크/매핑 인덱스를 전달하고 기존 DAG Run을 다시 실행 가능하게 만든다.
6. 현재 화면에서 실제 실행 상태를 추적한다. 페이지를 다시 열면 담당 범위의 최신 목록에서 확인한다.

미리보기는 5분 유효하며 실패한 DAG Run의 `failed`와 `upstream_failed`만 대상으로 한다.
성공한 태스크, 다른 날짜의 실행, 과거/미래 실행은 포함하지 않는다. 기존 DAG 버전을 유지한다.
한 번에 100개를 넘는 태스크와 실행 중인 Run은 native 실행 상세로 안내한다.
일시중지된 DAG는 담당 DAG 영역에서 먼저 활성화할 수 있다.
`model-lab` 태그의 DAG는 Model Lab에서 재요청하여 외부 작업의 중복 방지 계약을 유지한다.

미리보기 소유권·DB 행 잠금·같은 DAG Run 요청의 lease로 중복 요청을 제어한다.
완료된 확인 ID를 재전송해도 Clear를 다시 호출하지 않는다. 실제 요청 후 응답이 불명확하면
자동 재전송하지 않고 원본 상태 확인을 안내한다. Airflow의 별도 사용자/API와 함께 사용하는
환경에서 native Clear 자체의 원자적 조건부 실행을 새로 제공하는 것은 아니다.
실제 Clear는 현재 사용자의 인증으로 호출하므로 Airflow의 변경 권한과 감사 로그를 따른다.
플러그인 테이블에는 미리보기·확인 결과 상태도 남긴다.

## Airflow 메뉴와 링크 이동

FAB 역할은 `Plugins.menu_access`(메뉴 표시)와 `Plugins.can_read`(플러그인 목록/API 조회)를
함께 부여해야 한다. Viewer/User에 별도 `WorkbenchAccess` 역할을 추가하는 방식으로 설정한다.
`can_read`만으로 메뉴 노출까지 보장하지 않는다. 세 메뉴의 진입 권한은 공통이며 기능별 DAG
권한·프로젝트 역할 검사는 별도로 유지한다.

메뉴 등록은 Airflow의 `react_apps`를 사용한다. `shared/static/host.js`가 Airflow의 공유 React와
라우터를 사용하여 각 기능의 iframe을 마운트한다. `navigation.js`가 내부 링크 클릭을 전달하며
호스트는 현재 iframe의 window·같은 출처·허용된 Airflow 경로를 확인한다. 원본 `external_views`의
iframe은 상위 탐색을 막으므로 `_top` 링크만 사용하면 이동하지 않는다. 새 연결부는 상위 탐색
허용을 추가하거나 Airflow 코어 파일을 수정하지 않는다. 외부 원본 링크와 내보내기를 위해
플러그인 iframe의 popup/download 기능은 명시적으로 지원한다.

React 플러그인 공유 의존성 규약은 [공식 커스텀 UI 안내](https://airflow.apache.org/docs/apache-airflow/stable/howto/custom-view-plugin.html)를 따른다.
이 통합은 Airflow에서 experimental로 분류하므로 업그레이드 시 메뉴 로딩·링크·테마를 재확인한다.

## 운영 모니터링 연결

Workbench 설정 편집 권한이 있는 관리자가 **연결 설정**에서 이름·HTTP(S) URL·설명·표시 여부를
저장한다. 기존 Config 조회/custom Workbench 변경 권한 규칙을 재사용한다. 최대 20개 화면을
등록하며 활성 화면만 일반 Plugins 조회 사용자에게 노출한다. 화면별 Airflow ACL은 제공하지
않으므로 특정 외부 사용자/팀 제한은 외부 서비스의 권한으로 설정한다.

플러그인은 등록 URL만 브라우저에 전달한다. 서버가 URL을 대신 요청하거나 쿠키·비밀번호·토큰을
외부로 전달하지 않는다. URL의 사용자 정보와 대표적인 토큰 쿼리 항목은 거부한다. 비밀 링크를
등록하는 용도로 사용하지 않는다. 저장은 PostgreSQL `documents`의 `operations-monitoring`에 한다.

외부 서비스에는 다음 조건이 필요하다.

- Airflow 사용자 브라우저에서 접근 가능한 URL.
- 해당 서비스가 Airflow 출처의 iframe 표시를 허용하는 `frame-ancestors`/`X-Frame-Options` 설정.
- 외부 서비스의 로그인 세션과 조회 권한. 필요하면 **원본 열기**에서 먼저 로그인.
- 브라우저 쿠키 정책과 HTTPS 혼합 콘텐츠 정책에 맞는 배치.

SSO나 Airflow 역할의 외부 역할 매핑은 자동 구현하지 않는다. 이미 조직 공통 IdP를 사용하면
각 서비스에서 그 IdP를 연결할 수 있지만 iframe 자체가 SSO를 제공하지는 않는다.
외부 인증·임베딩 정책으로 표시할 수 없는 경우 원본 링크로 조회한다. iframe의 load 이벤트만으로
로그인/표시 성공 여부를 판정하거나 허위 정상 상태를 표시하지 않는다.

외부 frame 출처 허용은 운영 모니터링 HTML에만 적용한다. 나머지 플러그인 페이지의 CSP는
유지한다. 외부 화면이 다른 출처로 리디렉션한다면 최종 대시보드 URL을 등록하는 것이 좋다.
Grafana 테마 옵션은 URL의 `theme=light/dark`를 Airflow 설정에 맞춰 갱신한다. 다른 서비스의
테마는 해당 화면이 정하며, 플러그인이 외부 DOM을 바꾸지 않는다.

현재 연결 URL은 없다. 미등록 안내와 연결 설정 기능을 제공하는 상태이며 외부 SSO·권한 연동의
실환경 검증은 외부 서비스가 정해진 후 수행해야 한다.
